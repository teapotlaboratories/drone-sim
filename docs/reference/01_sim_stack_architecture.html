Drone Simulation Stack

Simulator landscape assessment and recommended triple-lane architecture for vision-based navigation, GPS navigation, obstacle and collision avoidance, and VLM experimentation — targeting sim-to-real transfer onto Pixhawk 6C + Jetson Orin NX.

§ 1 · DECISION

Verdict

Do not build on this Microsoft AirSim is dead. Development was discontinued 15 December 2023 and the team was laid off. Any tutorial, paper, or repo that assumes microsoft/AirSim is targeting an archived codebase. Its living descendants are Colosseum, Cosys-AirSim, and IAMAI's Project AirSim — and only two of those are viable here.

No single simulator satisfies all six requirements. Photorealism and iteration speed are in direct tension, and the benchmarks your target papers publish against are locked to a specific engine family. The correct answer is a triple-lane stack sharing one ROS 2 graph, where each lane earns its keep on a different axis.

Lane A · Baseline & CI

PX4 + Gazebo Harmonic

Lockstep, headless, deterministic, seconds-to-launch. PX4's officially supported default. Carries GPS navigation, controls work, and every regression test.

Build first

Lane B · Perception & RL

Isaac Sim 5.1 + Pegasus

RTX ray-traced cameras, stereo, depth, and Lidar. Domain randomisation for sim-to-real. Photorealistic perception training and VLM-in-the-loop evaluation.

Build second

Lane C · Benchmark repro

UE 5.5 + Cosys-AirSim

The only route to reproducing AerialVLN / OpenFly numbers, because Fly0 and OnFly evaluate on Unreal + AirSim-family engines. Highest integration risk.

Build last · optional

Load-bearing constraint Two version couplings dictate the entire architecture. Pegasus Simulator v5.1.0 was developed and tested against PX4 v1.14.3, not your pinned v1.16.x. And Isaac Sim 5.1 ships Python 3.11 while ROS 2 Jazzy on Ubuntu 24.04 is Python 3.12 — rclpy cannot be shared across that boundary. Both are resolved by separation, not by forcing convergence. See § 9.
§ 2 · SURVEY

Simulator landscape, 2026

The AirSim lineage fragmented after Microsoft's exit. Understanding which fork inherited what determines which one you can actually use on Ubuntu 24.04.

What each option actually is

  • Microsoft AirSim — archived. Microsoft stated it would release a successor platform and subsequently archive the original 2017 AirSim; reporting in October 2023 described the team being told the project would be discontinued, confirmed for 15 December 2023.
  • Project AirSim (IAMAI) — former Microsoft AirSim engineers, MIT-licensed, DARPA-supported. Supports Windows 11 and Ubuntu 22 only. Disqualified by the 24.04 requirement.
  • Colosseum (CodexLabs) — maintained fork on Unreal Engine 5.6, PX4/ArduPilot SITL and HITL. Its own README notes Ubuntu 22.04 is not supported due to Vulkan and recommends Docker — a real risk signal for native 24.04.
  • Cosys-AirSim (Univ. Antwerp) — the richest living fork on UE5 (targets 5.5): GPU-LiDAR, Echo sensors, annotation and instance-segmentation cameras, updated ROS 2 C++ wrapper, Nanite/Lumen, camera distortion models. External autopilot over MAVLink. This is Lane C.
  • Isaac Sim 5.x + Isaac Lab — general access from August 2025; 5.1 current, 6.0 in early developer release. RTX ray-traced sensors, modular ROS 2 bridge, OpenUSD asset pipeline. Drone/PX4 integration arrives via Pegasus.
  • Pegasus Simulator — BSD-3, ISR/IST Lisbon, the de-facto PX4-on-Isaac extension. v5.1.0 released 26 Oct 2025 for Isaac 5.1.0 and explicitly not compatible with older Isaac versions.
  • Gazebo Harmonic — PX4's official default. PX4 documents Gazebo Classic as downgraded to community support and no longer recommended for new projects. This is Lane A.
  • Aerial Gym Simulator (NTNU-ARL) — thousands of parallel multirotors, GPU raycast depth/Lidar/segmentation, SE(3) controllers on GPU. For RL throughput, not photorealism. Optional Phase 3+ addition.
  • Newton physics — contributed to the Linux Foundation in September 2025 by Disney Research, Google DeepMind and NVIDIA; 1.0 stable around March 2026. Swappable backend in Isaac Lab 3.0 / Isaac Sim 6.0, but validated on a limited robot set. Not a drone path yet — PhysX remains the default.

§ 4 · ARCHITECTURE

Recommended architecture

One ROS 2 graph, three interchangeable simulator backends, one autopilot interface per backend. The application layer — perception, planning, VLM client — never learns which lane it is flying in. That property is what makes sim-to-real transfer cheap.

Why this shape The application band is written once. Swapping lanes changes only which simulator process is running and which transport the autopilot speaks. use_sim_time is the single launch-level difference between simulation and flight; topic names, namespaces, and message contracts do not change.
§ 5 · INTEGRATION

PX4 ↔ ROS 2 interface

MAVROS is legacy. The current path is uxrce_dds_client compiled into PX4 firmware, talking to a Micro XRCE-DDS Agent, exposing uORB topics natively as ROS 2 topics via px4_msgs. px4_ros_com is now example code only.

Silent-failure rule px4_msgs must be branch-matched to the firmware. PX4 exports each build's uORB message set to the corresponding PX4/px4_msgs branch. A mismatch does not error loudly — topics simply never populate. From v1.16, message versioning additionally requires the ROS 2 Message Translation Node when versions diverge.

External simulators outside the Gazebo/SIH pair drive PX4 through the Simulator MAVLink API — HIL_SENSOR, HIL_GPS, HIL_ACTUATOR_CONTROLS, HIL_STATE_QUATERNION, HIL_OPTICAL_FLOW — with lockstep. Gazebo is the exception, using gz transport; SIH runs physics inside PX4 over internal uORB.

Forward-looking

Zenoh (rmw_zenoh) became Tier-1 in ROS 2 Kilted Kaiju with binaries for Rolling, Jazzy and Humble, and is a plausible future PX4↔ROS 2 middleware. It is not the default RMW today — do not build on it yet, but keep the RMW selectable by environment variable so a future swap is a config change.

VIO caveat — measure before you trust IMU–camera timestamp synchronisation is the recurring failure across every simulator. Isaac's Hydra-time RTX sensors plus the GPU IMU path are the most defensible option for VINS-Fusion, OpenVINS or ORB-SLAM3, but you must measure timestamp jitter and rate stability yourself before treating simulated VIO results as meaningful. Use Lane A lockstep as the control.
§ 7 · ENVIRONMENT

Photorealism and georeferenced terrain

Cesium streams Google Photorealistic 3D Tiles, Bing/OSM buildings and georeferenced WGS84 terrain into both Unreal and Omniverse — directly relevant to GPS-based navigation, since it gives you real-world coordinates under the aircraft. Cesium for Unreal can even stream Gaussian-splat payloads via 3D Tiles. Plugins are Apache-2.0.

Open blocker · verify before committing Cesium for Omniverse requires the Fabric Scene Delegate; FSD is mutually exclusive with PhysX. NVIDIA's own error text is explicit that FSD does not support physics simulation and that physics will be disabled. An NVIDIA engineer stated the combination cannot currently be worked around. This was still unresolved as of Isaac Sim 6.0 / Cesium for Omniverse 0.29.0.

Consequence: in Lane B, use Cesium for rendering and dataset generation only. Fly physics on baked static meshes. Georeferenced flight with physics belongs in Lane C (UE5 + Cesium for Unreal), where the conflict does not apply.

Other asset sources: Fab / Quixel Megascans with Nanite and Lumen for UE5; OpenUSD and SimReady assets for Isaac. On the research side, OpenFly integrates Unreal, GTA V, Google Earth and 3D Gaussian Splatting for real-to-sim rendering — the live direction for UAV environment realism.

§ 8 · VLM

What your three target papers actually used

These are the systems being replicated. They do not share a simulator, a benchmark, or a metric set — which matters enormously when you try to compare your numbers to theirs.

arXiv:2509.22653 · CoRL 2025

See, Point, Fly

Sim: Drone Racing League Simulator. Real: DJI Tello EDU via DJITelloPy.

Method: VLM annotates 2D waypoints on the image, projects to 3D displacement with adaptive step size.

Reported: SR 93.9% sim / 92.7% real. Cycle ≈1.5–3 s, VLM-inference-bound. Reports only SR + completion time.

arXiv:2602.15875 · NUDT

Fly0

Sim: Unreal Engine 4 + Microsoft AirSim. Benchmarks: AerialVLN and OpenFly.

Method: MLLM 2D grounding → depth back-projection → Lidar + EGO-Planner collision-free trajectory. 50 Hz control, ~0.5 Hz re-grounding.

Reported: AerialVLN SR 70.43%, NE 27.19 m. OpenFly SR 64.67%. Hardware: Pixhawk 6C Mini + PX4 + Jetson Orin NX 16GB.

arXiv:2603.10682 · SYSU/SUSTech

OnFly

Sim: 10 scenes in UE 4.27, 150-task bespoke benchmark.

Method: dual-agent — high-frequency target generator + low-frequency monitor. ESDF Fast-Planner.

Reported: SR 67.8%, OSR 78.1%, CR 2.7%. Onboard Jetson Orin NX, Qwen3-VL-4B-AWQ, TensorRT, FP16 ViT, KV-cache reuse, CUDA graphs. Decision ≈0.81 s.

Published numbers, side by side

Metric trap Success thresholds differ by a factor of four. AerialVLN and OpenFly define success as stopping within 20 m of the target; Fly0 and OnFly report against a 5 m threshold. Make the threshold a config parameter, or your numbers will be silently incomparable. Also note: OnFly reports no NE or SPL; SPF reports only SR and time; none of the three reports SPL.

The decomposition pattern

All three converge on the same structure — a slow semantic reasoner producing goals, and a fast geometric tracker executing them. This is the pattern to build against:

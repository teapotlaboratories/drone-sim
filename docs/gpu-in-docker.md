# How the GPU reaches the container

**Audience: another agent working on this stack.** This describes how a containerised Unreal
Engine renderer gets hardware-accelerated Vulkan on this specific machine, how to *prove* it is on
the GPU rather than falling back to software, and which parts are host-specific and will not
transfer.

Everything here was measured on **2026-08-06**. Where a claim is inferred rather than measured it
says so.

---

## 1. The short answer

The renderer runs hardware Vulkan on an **RTX 3080**. Verified four independent ways:

```
LogVulkanRHI: - DeviceName: NVIDIA GeForce RTX 3080
LogVulkanRHI: - API=1.4.341  Driver=0x988ac0c0  VendorId=0x10de
LogVulkanRHI: - DeviceID=0x2216  Type=VK_PHYSICAL_DEVICE_TYPE_DISCRETE_GPU

nvidia-smi compute-apps   323743  .../UnrealEditor   4280 MiB
gpu0 utilisation          72–78% sustained over 10 samples, gpu1 flat 0%
renderer CPU              459% of a possible 2400% (24 cores)
software-renderer strings 0 occurrences of llvmpipe/lavapipe/swiftshader
```

`VK_PHYSICAL_DEVICE_TYPE_DISCRETE_GPU` is the load-bearing token. A software rasterizer reports
`..._TYPE_CPU` and names itself `llvmpipe` or `lavapipe`. The CPU figure matters as much: software
rasterization would pin CPU near the 2400% ceiling **with the GPU idle** — the inverse of what is
observed.

## 2. The stack

| Layer | Value |
|---|---|
| Host OS | Bazzite (**Fedora-family** — this matters, see §4) |
| Container runtime | Docker Engine **29.6.2**, **rootless**, `fuse-overlayfs`, nested inside a distrobox |
| NVIDIA driver | **610.43.03** |
| NVIDIA Container Toolkit | **1.19.1** |
| GPUs | 0 = RTX 3080 10 GB (render) · 1 = RTX 5060 Ti 16 GB (inference) |

**`--ipc host` is refused by this daemon** (`error mounting mqueue … operation not permitted`)
under rootless/nested Docker. That is why `sim_up.sh` uses `--ipc shareable` on the renderer and
`--ipc container:sim-unreal` on the joiners rather than host IPC.

## 3. How the GPU is passed in: CDI, not the legacy runtime

This machine uses **CDI** (Container Device Interface), not the older
`--runtime=nvidia` / `NVIDIA_VISIBLE_DEVICES` path. The spec is generated by
`nvidia-ctk` and lives at:

```
/etc/cdi/nvidia.yaml
```

`docker info` enumerates what it provides:

```
CDI spec directories:  /etc/cdi-local
Discovered Devices:
  cdi: nvidia.com/gpu=0
  cdi: nvidia.com/gpu=1
  cdi: nvidia.com/gpu=GPU-961e3133-170e-e898-1f77-0bd7e59fe168
  cdi: nvidia.com/gpu=GPU-a59afb24-83b3-dc09-b197-345d1157b5a1
  cdi: nvidia.com/gpu=all
```

The renderer requests exactly one device, in `scripts/sim_up.sh`:

```bash
--gpus '"device=nvidia.com/gpu=0"'
```

> **The quoting is not decorative.** The inner double quotes are required by Docker's `--gpus`
> parser for a CDI device name; without them the `=` is mis-parsed. Keep them exactly as written.

**Pinning is real and verified** — inside `sim-unreal`, `nvidia-smi` lists only
`0, NVIDIA GeForce RTX 3080`. The 5060 Ti is invisible to the renderer, which is the documented
render/inference split (see `docs/bench.md`).

### What CDI injects

**Device nodes:**

```
/dev/nvidia0  /dev/nvidia1  /dev/nvidiactl  /dev/nvidia-uvm  /dev/nvidia-uvm-tools
/dev/nvidia-modeset
/dev/dri/card0  /dev/dri/card2  /dev/dri/renderD129  /dev/dri/renderD130
```

**Driver libraries**, bind-mounted from the host — `libcuda`, `libnvidia-*`, `libGLX_nvidia`,
`libEGL_nvidia`, `libnvcuvid`, plus GSP firmware under `/lib/firmware/nvidia/610.43.03/`.

**Hooks** — `/usr/bin/nvidia-cdi-hook` runs at `createContainer` to `create-symlinks` and update
the ld cache. This is why the libraries end up correctly linked without the image knowing anything
about the driver version.

Confirmed in a plain `ubuntu:24.04` container with nothing but the GPU flag:

```
/lib/x86_64-linux-gnu/libGLX_nvidia.so.0 -> libGLX_nvidia.so.610.43.03
/lib/x86_64-linux-gnu/libGLX_nvidia.so.610.43.03    (owned nobody:nogroup — a bind mount)
```

**The image needs no NVIDIA userspace of its own.** Do not install driver libraries into an image;
they would shadow the injected ones and break on the next host driver update.

## 4. The Vulkan ICD trap — the part that is genuinely host-specific

This is the one piece most likely to bite another agent, and the one that will differ on a
different host.

At runtime the engine container has **two** Vulkan ICD manifests:

```
/etc/vulkan/icd.d/nvidia_icd.json          "library_path": "libGLX_nvidia.so.0"       <- from the image
/etc/vulkan/icd.d/nvidia_icd.x86_64.json   "library_path": "/usr/lib64/libGLX_nvidia.so.0"  <- injected by CDI
```

The second comes from the **Fedora-family host**, where NVIDIA libraries live in `/usr/lib64/`.
The container is **Ubuntu**, where they live under multiarch at `/lib/x86_64-linux-gnu/`. The
absolute path in the injected manifest therefore does not resolve.

`docker/unreal.Dockerfile` closes this with one line:

```dockerfile
RUN mkdir -p /usr/lib64 \
 && ln -sf /lib/x86_64-linux-gnu/libGLX_nvidia.so.0 /usr/lib64/libGLX_nvidia.so.0
```

**This is load-bearing — verified by removing it.** Same image, same flags, symlink deleted:

```
LogVulkanRHI: Error: vpCreateInstance(...) failed, VkResult=-9
              with error VK_ERROR_INCOMPATIBLE_DRIVER
UnrealEditor exit 139
```

With it present, the renderer selects the 3080 and runs. Note that the bare-soname manifest alone
is **not** sufficient — a broken sibling manifest is enough to fail instance creation here, because
UE creates its instance through Vulkan Profiles (`vpCreateInstance`) rather than plain
`vkCreateInstance`.

> **The symlink target is itself a CDI-created symlink**, so it dangles at build time and resolves
> at run time. That is intended. Do **not** "fix" it by pointing at the versioned
> `libGLX_nvidia.so.610.43.03` — that hardcodes the driver version and breaks on a host update.

> **This is a path mismatch, not a driver incompatibility.** Driver 610.43.03 works fine once the
> loader can find it. Do not confuse it with the separate too-new-driver problem that blocks Isaac
> Sim and NVENC (`docs/nvenc-driver-blocker.md`).

**On a Debian-family host** the injected manifest would carry a multiarch path, the symlink would
be unnecessary, and it is harmless if left in place. This is tracked as an open design question in
`docs/todo.md` `SIM-19`: image, run command, or detection step.

## 5. Verifying it yourself

Run these against a live stack. Do not accept "the sim started" as evidence.

**a. Which device did the RHI select?**

```bash
docker logs sim-unreal 2>&1 | grep -aE 'DeviceName|VK_PHYSICAL_DEVICE_TYPE'
```
Expect `NVIDIA GeForce RTX 3080` and `..._TYPE_DISCRETE_GPU`. Anything naming `llvmpipe` or
reporting `..._TYPE_CPU` is software rendering.

**b. Is the process actually holding VRAM?**

```bash
nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv,noheader
```
Expect an `UnrealEditor` line with GB-scale memory. An empty list with a running renderer means it
is not on the GPU.

**c. Is there sustained graphics load?**

```bash
for i in $(seq 1 10); do
  nvidia-smi --query-gpu=index,utilization.gpu,memory.used --format=csv,noheader,nounits; sleep 1
done
```
Expect gpu0 in the tens of percent, gpu1 at 0. A busy renderer at 0% utilisation is the signature
of software rendering.

**d. Rule out a fallback explicitly.**

```bash
docker logs sim-unreal 2>&1 | grep -acaiE 'llvmpipe|lavapipe|swiftshader'
```
Expect `0`. UE names its fallback when it takes one.

**e. Check the CPU shape.**

```bash
PID=$(nvidia-smi --query-compute-apps=pid --format=csv,noheader | head -1 | tr -d ' ')
ps -p "$PID" -o %cpu=,%mem=
```
~450% across 24 cores is normal for GPU rendering plus game and physics threads. Near 2400% with
an idle GPU is software rasterization.

**f. Confirm the pin.**

```bash
docker exec sim-unreal nvidia-smi --query-gpu=index,name --format=csv,noheader
```
Expect exactly one line: the 3080.

## 6. Failure modes and what they look like

| Symptom | Cause |
|---|---|
| `VK_ERROR_INCOMPATIBLE_DRIVER`, `vpCreateInstance` fails, exit **139** | The `/usr/lib64` ICD path (§4). The symlink is missing or the base image changed. |
| `Refusing to run with the root privileges.` then abort, exit **134** | UnrealEditor will not run as root. Never pass `--user root` to the renderer — this will masquerade as a GPU problem. |
| Renderer runs, gpu0 at 0%, CPU pegged | Software fallback. Check §5a/§5d. |
| `nvidia-smi` empty inside the container | The `--gpus` flag was dropped or the CDI device name is wrong. Check `docker info` for `Discovered Devices`. |
| Renderer starts then exits with no Vulkan lines at all | Usually not GPU: check `GlobalDefaultGameMode` (see `docs/worlds.md`) — AirSim never instantiating looks similar from outside. |

> **A trap worth stating.** While testing this I removed the symlink *and* passed `--user root` so
> I could delete it, then read the resulting abort as proof the symlink mattered. It was not — root
> refusal was killing it. The valid test builds a throwaway image that removes the symlink as root
> and then runs as `ue4`. **Change one variable at a time**, and prefer an image layer over a
> runtime `--user` override.

## 7. Known limits

- **NVENC is unavailable** on driver 610.43.03 even though CUDA works. This is a driver-level
  refusal, not a container issue; video encoding is CPU x264. See `docs/nvenc-driver-blocker.md`.
- **10 GB VRAM on the render card** is the real ceiling for world choice. Epic's `Big_City_LVL`
  does not fit; `Small_City_LVL` does at ~4.5 GB with Blocks-scale content.
- **Do not swap the GPUs.** The 5060 Ti's 16 GB is reserved for inference. `sim_up.sh` pins device
  0 at the container boundary because `-RenderOffScreen` has historically ignored
  application-level GPU hints.

## 8. Porting this to another machine

What is **portable**: the CDI mechanism, the `--gpus '"device=nvidia.com/gpu=N"'` form, expecting
no NVIDIA userspace in the image, and every verification command in §5.

What is **host-specific**: the `/usr/lib64` symlink (Fedora-family hosts only), the exact device
node list, and the driver version in every injected path.

Regenerate the spec on a new host with `nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml`,
then check `docker info` shows the devices before touching anything in this repo. If the renderer
fails on Vulkan, read the injected manifest's `library_path` and compare it against where the
library actually landed in the container — that single comparison is what §4 is.

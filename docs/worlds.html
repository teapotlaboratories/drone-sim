Bring Your
Own World

Take an Unreal project that was never built for this simulator and fly a drone in it. Two commands do the work. This page is about the four ways it fails — every one of them silent, every one hit for real converting Epic’s CitySample, and every number here measured rather than quoted.

Steps 4 Tiers A1 · A2 CitySample flies Reliability 2 in 3 
./scripts/convert_world.sh /path/to/Your.uproject --map /Game/Maps/YourMap
./scripts/sim_up.sh       --world /path/to/Your.uproject --spawn 0,0,-50

The first converts and builds. The second flies it. Everything below is what those two lines do, and what to do when they do not work.

01 Will it work at all?

RequirementWhy
UE 5.8The engine is pinned. A 5.2–5.5 project usually compiles, but expect warnings-as-errors.
Linux-buildableWindows-only plugins or Win64-only binaries will not link.
Fits 10 GB VRAMThe render GPU is the 3080. Big_City_LVL does not fit; Small_City_LVL does.
Internal NVMeUE5 streaming is latency-sensitive random I/O. A spinning disk works, loads slowly, and loses the streaming race more often.
A1 or A2 — the only question that changes the cost

If the project has a Source/ directory it is A2: its C++ must be compiled against UE5.8, and that is where the time goes. Content and Blueprints only is A1.

The script detects this and prints it. It also changes which build target is used, and getting that wrong is failure mode #2 below.

02 What the conversion does

1 · Inject — the failure with no error message

inject_airsim.py copies the built plugin, enables it, and sets two config keys. The one that matters:

GlobalDefaultGameMode=/Script/AirSim.AirSimGameMode
Skip this and nothing works, and nothing says so

The project keeps its own game mode, AirSim never instantiates, nothing ever listens on TCP 4560, and PX4 sits forever in Waiting for simulator to accept connection on TCP port 4560. There is no error line. Both City Park and CitySample hit this — CitySample’s was BP_CitySampleGameMode.

Raising SIM_LINK_TIMEOUT will never help, which is the trap: the symptom looks exactly like a slow load.

Pass --map as well. A content path that does not resolve is written into config without complaint and then fails the same silent way, so the script now verifies the .umap on disk before touching anything and lists the maps the project really has. That check exists because a plausible-looking /Game/Maps/Demonstration was accepted for a project whose map is /Game/CityPark/Maps/Showcase.

2 · Patch — the vendored tree stays pristine

vendor/Cosys-AirSim is byte-identical to upstream. Deviations live in patches/cosys-airsim/ and are applied to the injected copy. If a patch neither applies nor reverse-applies, the conversion stops rather than continuing quietly — skipping 0005 produces a world the drone falls through, which is precisely what it prevents.

3 · Build — two things break on any project older than 5.8

-Werror on unreachable code

UE5.8 ships a newer clang and promotes -Wunreachable-code-break and -Wunreachable-code-loop-increment to errors. On CitySample that hit 14 files — across Epic’s own RuleProcessor and Traffic plugins and Cosys-AirSim. Downgrade exactly those two; do not disable warnings-as-errors wholesale.

UBT then refuses the compiler args

The editor target shares build products with UnrealEditor, so UBT rejects per-target args and suggests TargetBuildEnvironment.Unique — which forces a full engine rebuild, hours for two warnings. bOverrideBuildEnvironment = true is the cheap door.

Both go into your <Name>Editor.Target.cs, backed up to .pre-airsim first. Build the editor target: sim_up.sh runs UnrealEditor <project> -game, so the editor modules are what must exist.

03 World Partition — the one that costs a day

Symptom: the level loads, PX4 connects, and the drone falls forever. Bring-up fails with no finite EKF origin — pointing at the EKF, which is innocent.

Releasing higher only buys more fall, which is how you know it is not a spawn-height problem and not the underground-spawn trap. Measured on CitySample, resting z in NED, where +z is DOWN:

SpawnResting zResult
0,0,0+332 mfell through
0,0,-150+139.5 mfell through
0,0,-150 + wp.Runtime.EnableStreaming=0+1481 mfell through — the cvar route does not work
0,0,-150 with 0005−0.00008 mon the ground
Necessary but NOT sufficient — a race remains

Cell streaming takes seconds (GenerateStreaming measured 7–22 s) while the vehicle falls immediately. It can still pass the ground plane before the cells beneath it activate. Measured on identical builds and the same spawn:

run 1   z = -8.4e-05 m   flew, 5/5 nav checks
run 2   z = +1697 m      fell through
run 3   z = -1.0e-03 m   flew, 4/4 waypoints, worst 0.855 m

Roughly 2 runs in 3 succeed — retry on failure. A real fix must hold the vehicle until streaming completes rather than race it. Unsolved; tracked as SIM-21.

04 Verifying — the part people skip

A level that renders is not a world that flies. Judge by resting z, not by the log.

docker exec sim-ros2 bash -lc 'source /opt/ros/jazzy/setup.bash; \
  source /ros2_ws/install/setup.bash; ros2 topic echo --qos-reliability best_effort \
  --qos-durability volatile --once --field z /fmu/out/vehicle_local_position'

Two measurements that lie

Counting LogWorldPartition cell-load lines is a bad proxy. UE does not log per-cell activation at default verbosity, so the count reads 0 even when streaming works. It reported failure on a run that flew perfectly.

A rebuild may never reach the pawn that runs. AirSim spawns a Blueprint subclass (BP_FlyingPawn_C), not the C++ class, so a change that did not propagate looks identical from outside. If you are changing pawn C++, log from BeginPlay and read it back out of the running renderer — verify the artifact that ran.

05 Troubleshooting

SymptomCause

Build fails on another -Werror warningAdd it beside the two, same form, in <Name>Editor.Target.cs.
Build succeeds, wrote NO shared objectThe target compiled nothing for this project — usually the wrong target.
Wrong target on a project with severalThe script prefers <Name>Editor. A bare *Editor glob sorts alphabetically and picks e.g. FooCookedEditor — a cooking target, not the one -game runs.

Vehicle spawns undergroundRelease from height with --spawn X,Y,-Z and read the resting position back — that is a ground probe. Z is NED: negative is up.

06 What it leaves behind, and what is still missing

In your project — all reversible:

  • Plugins/AirSim/ — --force moves any existing copy aside to AirSim.bak.<timestamp> rather than overwriting.
  • Config/DefaultEngine.ini — game mode, map, SF_VULKAN_SM6, cook directives. Backed up .pre-airsim.
  • Source/<Name>Editor.Target.cs — the two build settings. Backed up .pre-airsim.
  • Binaries/, Intermediate/ — build output.
Known gaps

inject_airsim.py copies the built plugin from Blocks, so 0005 does not travel with it — convert_world.sh applies it to the project’s own copy and rebuilds. That is why an A1 project still needs a build. Wiring the Unreal-side patches into the Blocks plugin build is unsolved.

CarPawn has the same World Partition gap and is deliberately untouched — nothing here drives a car.

A stale plugin copy under Plugins/ silently wins. inject_airsim.py refuses rather than guess when it finds two.

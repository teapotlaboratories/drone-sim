What’s In
These Images

Six images, ~80 GB on disk, and nothing is broken — every one builds and the stack flies on them. This is about what they contain: about half the PX4 image is build-time material that no running container ever reads, and three of the four derived images inherit a base they use nothing from.

PX4 image 11.0 → 4.73 GB Slice 1 built, unverified Slice 2 not started Constraint pull time, not disk
The thing being bought

Not disk. There is 189 GB free and image size has never been this project’s constraint. What is being bought is pull and build time on a fresh machine — the exact scenario the “reproducible as Docker” goal exists for. Docker counts a shared layer once per image in docker images, so the four derived images do not cost 46 GB of disk; docker system df reports ~80 GB total, dominated by the engine.

Where those two things come from, exactly

1 · The NuttX / ARM toolchain — ~2.9 GB

docker/px4.Dockerfile:124
RUN bash Tools/setup/ubuntu.sh --no-sim-tools

PX4’s own setup script installs the ARM cross-compiler unless --no-nuttx is passed. It was deliberately not passed, and the reason is good: real Pixhawk 6C firmware is flashed from this same tree, and --no-nuttx would have slimmed the image while silently removing that capability.

Largest packages: libstdc++-arm-none-eabi-newlib 2014 MB, gcc-arm-none-eabi 493 MB, libnewlib-arm-none-eabi 417 MB.

2 · The PX4 source tree — ~2.5 GB

docker/px4.Dockerfile:119
RUN git clone --recursive --branch ${PX4_TAG} \
    https://github.com/PX4/PX4-Autopilot.git .

--recursive pulls every submodule, which is why .git alone is 1.5 GB. The clone is required — the SITL binary has to be compiled from it. What is not required is keeping it afterwards: the runtime reads only build/px4_sitl_default/.

Correction — the entry was wrong twice, and both were caught by measuring

openjdk (286 MB) is NOT PX4’s. SIM-19 listed it as installed by Tools/setup/ubuntu.sh. It is present in the base stage, before PX4 is cloned — it arrives through ROS via default-jre-headless ← default-jdk-headless. A stage split cannot remove it, so it is not part of the win. Removing it means first answering what in the ROS toolchain needs a JRE.

And earlier: ros-jazzy-desktop was not the problem either. The entry originally called it “almost certainly the wrong metapackage” and the biggest win. /opt/ros/jazzy is 236 MB, and the wrapper genuinely needs cv_bridge, image_transport, pcl and pcl_conversions, which ros-base does not carry. That lead was written from a guess and measurement killed it.

03 The plan — two slices

Slice 1 — strip the PX4 image · BUILT

No renaming, no restructuring of other images, zero reference churn. The toolchain and source tree stay in a --target firmware stage; the runtime copies only build/.

11.0 GB → 4.73 GB, measured. Every derived image inherits the saving.

Runtime assertions in the Dockerfile check the SITL binary and rcS are present and the toolchain and source are gone — so the strip cannot silently regress.

Slice 2 — the structural split · NOT STARTED

qgc and video off the PX4 base entirely; a shared base for px4 and ros2 only.

Bigger, and it needs the naming decision below. Known detail: qgc leaving the PX4 base must re-add curl, ca-certificates and /etc/drone-sim-versions, which it currently inherits.

A smaller image that does not fly is a regression

Since SIM-37 the wrapper is baked into drone-sim/ros2, so a stack brought up by sim_up.sh already has the sensor graph — this script is no longer part of bring-up. It rebuilds the wrapper inside a running container (deleting the image’s copy first), which is how a wrapper patch gets tested without a full image rebuild.

The acceptance gate is unchanged and has not been run: the wrapper builds, the stack comes up through all three bring-up barriers, and the example mission flies. Until then “4.73 GB” is a size, not a result.

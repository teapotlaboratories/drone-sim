Decision — 2026-07-31

All-in on Lane C. Cosys-AirSim on UE5.5 is the primary simulator, and Phase 2 — perception and obstacle avoidance — moves off Gazebo. The reasoning is in docs/reference/04_ue5_stack_architecture.md: all three target papers evaluate on Unreal/AirSim-family simulators, Microsoft AirSim was archived 2023-12-15 and Colosseum 2026-07-11, so Cosys-AirSim is the only live option meeting every hard requirement. Building Phase 2 in Gazebo would mean building it twice.

Three questions that report left open were settled at the same time:

  • Lane A is demoted, not retired — always-on regression baseline. It keeps tier-1 CI, the flight gate, and the real-hardware PX4 tree.
  • ROS 2 stays Jazzy, against the report's Humble recommendation — that recommendation is inherited from upstream example docs, while every pin here is Jazzy and measured.
  • Phases are mapped, not renumbered — the report's phases are calendar weeks; ours are capabilities with measured exit criteria.
  • The engine pin moved UE5.5 → UE5.8 (tag 5.8-v3.4.1), surfaced by research hours after the decision: UE5.5 and Jazzy cannot be had from one upstream tag, and the UE5.5 branch is end-of-life. Measured here — ros-jazzy-cv-bridge 4.1.0 ships no cv_bridge.h, so that tag is unbuildable on this machine. Cesium gate cleared the same day: Cesium v2.28.0 supports UE5.8, and v2.29.0 drops UE5.5 — so the fallback inverted and UE5.8 is the only forward-supported path.

Two findings from clearing that gate change work beyond the pin. The Epic engine image is Ubuntu 22.04, and ROS 2 Jazzy has no jammy packages — so the separate sim and ros2 containers become mandatory rather than stylistic, and building the wrapper in the existing 24.04 container (which is what C-06 already does) is now the only option. And building this lane needs an EpicGames org credential, which is a real gap against “a fresh machine reaches a working stack from the repo alone”.

That was written when Lane C had never been built. It has now been built and flown — see the update below. Lane A still stays alive as the regression baseline, and that decision looks better rather than worse: four of the five failures hit while bringing Lane C up were already written down in Lane A's notes.

Update — 2026-08-01 / 08-02

Lane C flies. The unmodified Lane A offboard_control node reaches 4/4 waypoints in Cosys-AirSim on UE5.8 — max error 0.79 m, reproduced three times including from a cold start. The controller was never patched; only the transport was swapped. That is the sim-to-real parity claim demonstrated end to end rather than argued.

C-03 proved it first as a diff: 51 /fmu/ topics, 24 /fmu/out, byte-identical between Gazebo and Unreal. The perception graph is now up alongside it — 19 /airsim_node/ topics carrying 640×480 RGB, depth, camera_info and an 8192-point GPU-LiDAR cloud.

Three things cost real time and are worth carrying forward:

  • A stale PX4 EKF origin made the vehicle report 35 m of altitude while parked on the ground, which presents exactly as a control bug. scripts/lane_c_up.sh now verifies and repairs the origin on every bring-up (4 for 4), and the gate VOIDs such runs rather than scoring them as failures.
  • Lockstep is confirmed dead code in Cosys-AirSim — the flag is set once and cleared twice, and the activation message never fires. "LockStep": true is silently ineffective, so every Lane C timing number is free-running and none may be quoted as deterministic.
  • The AirSim ROS 2 wrapper aborted on first publish from an upstream data race (Reentrant callback group on a MultiThreadedExecutor). Fixed as a recorded patch; vendor/ stays pristine.
Update — 2026-08-03 · the imagery is photorealistic

simGetImages now matches Unreal’s own render of the same camera actor at the same transform to 1.15 of 255, across six scenes from close-up to 70 m. The long-running “the AirSim capture looks washed out” turned out to be three unrelated faults wearing one costume:

  • the measurement client read the buffer as BGR when Cosys-AirSim returns RGB — which does not look like a bug, it looks like a plausible cyan colour cast;
  • the camera was inside world geometry, and a near surface blurred by depth-of-field is itself a film over everything behind it;
  • PIPCamera.cpp:701-715 does not merely skip Lumen when the default is false — it forces global illumination and reflections to None, in a world authored for Lumen.

The fix is three settings.json keys on a stock plugin binary — LumenGIEnable, LumenReflectionEnable, ForceUpdate — costing ~8.6% RGB and ~10% LiDAR on the real graph. C-13 landed the same day: the operator can now pass --spawn X,Y,Z[,YAW] when starting the simulator, and the vehicle holds position with 0.000 m drift over 6 s unheld, retiring a pose-holding workaround.

Two corrections worth more than the fix

The previous day’s negative result was VOID. Unreal de-duplicates plugins by name+version and had silently loaded a stale backup left inside Plugins/; the patched binary was never loaded. The md5 check that “verified” it inspected the file on disk, not the one the engine resolved. Verifying that an artifact exists is not verifying it was used.

The “31 Hz RGB / 29.6 Hz depth / 17.4 Hz LiDAR” figure is retired. It does not reproduce — stock settings now measure 18.7 / 18.1 / 10.0 Hz on the same grey-box world. It predates lane_c_perception.launch.py, which pins the poll periods at 20 Hz imagery and 10 Hz LiDAR, so today’s numbers sit at 94% and 100% of their ceilings. The clearest tell: 17.4 Hz from a sensor configured RotationsPerSecond: 10 was reporting poll rate, not data rate. Nothing regressed; the old number measured the wrong thing.

03 Phases are not lanes

Everything shipped so far is Lane A — and everything from here is Lane C. The phase axis above hides a second one, and the two are easy to conflate: a phase is a capability, a lane is a simulator. On 2026-07-31 the lane axis changed underneath the phase axis, without moving a single phase boundary.

The long pole — now someone is holding it

This page previously said Lane C was "the long pole nobody is holding": five tasks, all todo, with nothing forcing a start until Phase 3 needed it. That is resolved — by making it the critical path rather than by de-risking it.

The risk itself is unchanged and should not be read as smaller: the plan rates Lane C High likelihood / Med impact for build fragility, the precompiled Cosys-AirSim Linux plugin targets UE5.2.1, and the UE5.5 branch was a March-2025 pre-release. C-01 is still literally "find a commit that builds". What changed is that this is now discovered first, at Phase 2, instead of as a surprise during Phase 3 — and that Lane A is kept alive underneath it rather than retired.

The order was chosen to fail cheap. C-06 — compile the Cosys-AirSim ROS 2 wrapper against Jazzy — runs before the multi-hour UE5 engine build, because it is an ordinary colcon package that needs no engine, no GPU and no simulator, and it is the one test that can invalidate the ROS 2 distro decision.

Next: C-11 — actors in the user’s world

The world is photorealistic and the drone can be placed in it deliberately. What it has no people, vehicles or moving obstacles — the other half of “a photorealistic simulator with actors”.

The path needs no project C++ and no plugin change. The RPC surface (simListAssets, simSpawnObject, simSetObjectPose, simSetObjectScale, simDestroyObject, plus simAddDetectionFilterMeshName for ground-truth labels) works in any project, preserving the A1 drop-in property. simGetObjectPose was exercised against City Park on 2026-08-03, so that surface is known live in this build rather than assumed.

One decision to make deliberately: the vendored -startSeed/-spawnAI determinism lives on the C++ side — adding a Source/ module turns A1 into A2, breaking bring-your-own-world for exactly the feature the eval gate needs. Seed it in our own scenario harness instead (seeded RNG → spawn poses → record the seed): reproducible in any world, no vendor change, and squarely the “glue is the original work” split this project is built on. Reimplementing a vendor feature normally deserves suspicion; here the vendor’s version is unusable without abandoning A1.

First step, deliberately small: spawn a few actors into City Park over RPC, confirm they appear in both RGB and GPU-LiDAR, and re-measure rates with actors present — RGB already sits at 17.1 Hz against a 20 Hz cap. (The old “the segfault gets likelier with more actors” caveat is withdrawn — it never had a measurement behind it, and a 90-minute full-stack soak on 2026-08-03 did not reproduce the crash at all.)

Deferred on purpose, with the reason recorded

C-12 — the capture carries more high-frequency speckle than Unreal’s render. ForceUpdate removed the Lumen-attributable part (−13.9%, free), and a Lumen-off control proved that is exactly what it denoises. The residual number is not trustworthy: it survives 2× supersampling, which real edge aliasing would not — so much of the “2.5× noisier” is likely native’s TSR softening the reference. The first task there is a better metric, not a better fix.

C-14 — automatic spawn siting, unblocked for free by C-13: spawn-and-settle is a ground probe. Release high, read simGetObjectPose, and the resting Z is the terrain surface. Settings plus RPC only; no plugin change, which was the open question it was blocked on.

The constraint C-05 inherits, measured

The IMU is 78% duplicates. airsim_node publishes at 1501 Hz but only 6630 of 30022 messages carry a distinct timestamp — the real sensor runs at ~333 Hz, with gaps up to 3× the base interval. The 1501 Hz is the RPC poll rate, not a sensor rate.

This is measured, not fixed, and it is a live design input: cuVSLAM and any preintegrating VIO want a dense, evenly-spaced stream, and this is the bad case on both axes — repeated timestamps and non-uniform spacing. ros2 topic hz reports a healthy-looking 1501 Hz at 0.17 ms jitter and tells you none of it.

Owed before more work stacks up

/review has not run on either open PR, and that is the project's own merge gate. The branch is 14 commits deep behind it and still growing; the longer it runs, the more expensive the findings are to act on.

Also carried: the AirSim wrapper fixes exist as recorded patches but docs/vendor/cosys-airsim.md is still unwritten, and vendor/Cosys-AirSim/ros2/ holds 163 MB of build artifacts from an in-tree build — gitignored, so invisible in a diff, but it broke a build once.

Substrate — decided 2026-08-01

The target is Docker on a native machine. The distrobox on this box is scaffolding, not the architecture. That shrinks the reproducibility task rather than growing it: nothing needs to capture distrobox create, but three host-specific workarounds need auditing before they are mistaken for general fixes — chiefly the Vulkan ICD symlink, which exists only because a Fedora-family host injects /usr/lib64 paths into an Ubuntu container.

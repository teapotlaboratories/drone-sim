03 The four connections that matter

PX4 ⇄ Gazebo

Not a network hop. gz sim runs inside lane-a-px4, started by PX4's own launch — which is why that container shows both px4 and ruby (Gazebo's launcher) as processes.

PX4 ⇄ ROS 2 — two hops

PX4 → agent over UDP on loopback (:8888); agent → ROS 2 over DDS shared memory. Sharing the network namespace alone was not enough: topics appeared in ros2 topic list while ros2 topic echo returned nothing, because each container had its own /dev/shm.

PX4 ⇄ QGroundControl

PX4 binds 18570, QGC binds 14550, and QGC starts the conversation by sending to 18570. This is the datalink PX4 requires before it will arm — stop this container and arming is denied.

QGC ⇄ recording

The xsock volume shares the X socket, so the recorder draws its panes on QGC's display and captures QGC's own window — instead of starting a second QGC that would fight over PX4's learned remote address.

The handshake, and the silence it explains

Nothing is ever sent to 14550 until a ground station speaks first: PX4 has no preconfigured remote, so QGC discovers by sending to 18570, and only then does PX4 learn QGC's address and reply to 14550. Proven both ways — binding 14550 on a fresh stack received nothing in 8 s, while binding 18570 failed with EADDRINUSE because PX4 already held it.

A MAVLink heartbeat aimed at 14550 is therefore discarded with no error and no log line, and the datalink simply never comes up. Both ports are published; neither is redundant.

05 Two traps this shape creates

Never recreate lane-a-px4 alone

Every other service joins its network namespace. Recreating the donor by itself leaves them attached to a namespace that no longer exists — and the symptom is brutal: every container still reports healthy while ros2 topic list returns zero topics. It reads as a broken simulator rather than a container-plumbing mistake.

Measured: 0 topics after recreating px4-sitl alone, 24 after recreating everything. The seeded scenario runner always recreates the whole stack for exactly this reason.

Only the donor may publish ports

Because the others have no network stack of their own, ports: on any service but px4-sitl is meaningless. The same applies to shm_size: declaring it on a joiner is inert, since it uses the donor's /dev/shm. Both are commented in the compose file so the next reader does not add them back.

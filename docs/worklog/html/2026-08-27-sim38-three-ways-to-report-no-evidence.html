01 Why it was not just a flag

record_topics was already generic — a scenario could always name any topic. What it could not do was make the topic exist: sim_up.sh does not start airsim_node, so a scenario listing depth recorded an empty topic and still reported success, because the topic was listed, the recorder ran, and the bag exists.

sensors:
  - depth
  - lidar
  - imu

So it does three things: starts the perception graph and blocks until topics appear; appends to record_topics rather than replacing it, with cameras bringing their camera_info; and counts the messages in the bag afterwards, failing the run if a requested sensor recorded nothing.

03 Three bugs, one shape

The third one is the repo’s own documented trap

dexec runs docker exec without a login shell, so ROS is not on the path and import rosbag2_py fails with ModuleNotFoundError — swallowed by the except. This project documents that trap in three places and bakes ros-profile.sh into the image to avoid it, and it still caught me. Fixed with bash -lc, and the script passed via docker exec -e rather than interpolated, so a topic name containing a shell metacharacter cannot be executed.

The tests added here pin those three failures rather than the happy path: counting must use a login shell, evidence must attach to every return path, and the vocabulary must match verify_sensors.py.

04 Cost, measured

Perception adds ~30 s of settle per bring-up, and on CitySample the rates are about a third of what Blocks posts — depth ~10.5 Hz, GPU-LiDAR ~5.5 Hz — under real scene load. Bags go from ~840 KB to 2–2.6 GB.

Default off, and per-scenario

The owner’s call was that the bag matters more than its size. So it is declared per scenario rather than globally: a 40-seed gate would pay that cost forty times, and the scenario is where the decision belongs.

Left undone: rgb is in the vocabulary but untested — every run so far declared the other six, because the vehicle camera video and the chase view already cover it.

05 Appended after review — a fourth of the same shape

Review of PR 64 found seven issues. The one that matters is the fourth instance of the pattern this page is named for, one level up from the first three: count_sensor_messages returned a bare {} for every failure mode, and the caller printed one stderr line and left the run scoring PASS. “The bag cannot be read” and “the bag is fine” took the same branch again — in the function written to stop exactly that.

And this feature is what makes it reachable

Bags went 840 KB → 2.6 GB, while the recorder waits 60 s and then kills the docker exec client, not the in-container writer. An mcap that has not finalised in that window has no metadata.yaml, the read raises, and a run whose bag is genuinely broken reports success with sensor_message_counts: null. The counter now returns why, and the run is VOID — the same call the stale-EKF-origin check makes, and not the softer verdict: any void blocks the criterion outright, where a failure only lowers a percentage.

Fixing that then created a worse bug than the one it fixed, caught before it shipped: a run that had already failed for a real reason and also had empty sensors was being converted to a void — and voids are excluded from the success rate, so a flight that crashed and lost its sensor graph would have vanished from the number entirely. The void now applies only to a run that was otherwise passing.

The last one measured better than either proposal

Info().read_metadata on the .mcap file itself counts correctly with metadata.yaml present and absent — the unfinalised case above — while SequentialReader cannot open that bag at all. It also reports a topic with zero messages, which a walk cannot, and that topic is the entire point of the check. Verified in the container against a real bag across all three states: finalised, no metadata, no bag.

Then checked against the real bags, not a synthetic one

Both archived flight bags are still on disk, so the new counter was run over them — no flight needed. It reproduces every number in the table above exactly, on both worlds, in 0.08 s each instead of re-reading 2.0 and 2.6 GB. Not a plausible-looking substitution: the same answer as the walk it replaced, on the same evidence, three orders of magnitude faster.

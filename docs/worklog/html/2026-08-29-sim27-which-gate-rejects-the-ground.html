The Ground
Was A Wall

Only one branch in AirSim’s integrator stops a descent, and reaching it means passing three gates that answer “is this the ground?” from a collision normal alone. Which gate fails on CitySample has been the ticket’s central unmeasured claim for three weeks. It is now instrumented, flown — and the answer is not yet, for a reason worth writing down.

01 The question

The ground lock at FastPhysicsEngine.hpp:228 is the only branch that stops a descent: it zeroes velocity, snaps the body to the contact point and sets grounded. Reaching it needs all three of:

GateTestWhere
Athe contact is not separating — normal · next_velocity < 0:141 early return
Bit looks like ground (|normal_body.z()| ≈ 1, tol 0.25) and like a landing:156, :163
CEnableGroundLock, default true:228

A and B imply different fixes, so step 3 must not be written until this is measured. Everything in the ticket up to now was read from source and never observed running.

02 The probe, and what it cost to be sure of it

patches/cosys-airsim/experimental/0008 adds no behaviour — it prints what the engine already decided. Verified before spending a build: applies cleanly to both plugin trees, and a standalone g++ -fsyntax-only of the patched and pristine headers produces identical output, so nothing the real build says afterwards is the patch’s fault.

Two details that cost time

The logger must be static: getNextKinematicsOnCollision is a static member and cannot reach the existing throttledLogOutput, which needs instance state. And the header is CRLF — cutting the patch in Python text mode rewrote every line ending and produced a 478-line whole-file diff instead of a 47-line one.

The shadowing trap was checked rather than assumed: the world holds five AirSimBackups/ trees with their own .uplugin files, but they sit at the project root, not under Plugins/ — deliberate, per inject_airsim.py:219 — and the .uproject declares no AdditionalPluginDirectories. Still only files on disk, which is exactly the evidence that misled this project before. The flight is what settled it.

03 Flown — CitySample, seed 1

Bring-up needed the usual ground repair (the vehicle fell to z = +813 before being placed at +0.756), then the origin was sane to 0.000 m. 513 SIM27 lines appeared, which settles what the file checks could not: the engine loaded the instrumented binary.

04 The instrumentation had a flaw, and the run found it

Not one gate=C line, from a landing that ground-locked

sim27Log used one throttle timer for every call site. Gates B and C are logged microseconds apart in the same call, so B’s line always reset the timer and C’s was always suppressed. A throttle shared across call sites cannot answer a question about which call site fires.

Fixed (per-gate timers), re-cut, syntax-checked, and rebuilt into the world so the next seed needs no preparation. The counts above stay indicative only: a wall-clock throttle samples the first call in each window, so they are not frequencies.

05 The new detector’s first live CitySample run

max_pose_split_m = 0.891 m — over the 0.5 m reporting threshold, so it printed the informational line, and correctly did not trip: that sample sits at vz = -3.028, i.e. ascending, which the sign condition excludes. Worst descending gap was 0.186 m, consistent with the corpus worst of 0.255 m.

The review’s skew correction is a guard, not a tax

The new gap field says the two RPCs are essentially simultaneous: median 0.000 s, max 0.002 s. So the 0.891 m divergence is not RPC-gap skew — it is genuine actor-versus-integrator lag during a 3 m/s climb. The correction costs nothing here, and the thing actually protecting against that sample is the sign condition.

06 Answered — it is gate B

Three CitySample seeds, cold stack each so the spawn pose applies. 3 of 3 split, all caught live by the step-2 detector and VOIDed — its first true positives outside replay. The gate report reads INCONCLUSIVE — 3 run(s) VOID, success rate 0/0 (0%) [3 VOID excluded]: no laundered percentage, no control failure, the cause named.

16:53:30.845  gate=B-NORMAL abs_nz=0.00027 tol=0.25 is_ground_normal=0 | z_vel=0.692 is_landing=1 | lock_enabled=1
16:53:30.845  gate=C-NO-LOCK ground_collision=0 lock_enabled=1 nextvel_z=0.684

… and that pair again, 295 times, for 141 seconds, while the integrator accelerated from 0.684 to 2.452 m/s. abs_nz ≈ 0 is a normal perpendicular to the vertical axis — the engine is being handed a wall. It asks “is this the ground?”, the normal says no, ground_collision stays false, and the only branch that could stop the descent is never reached.

Why widening the tolerance is not the fix

Healthy touchdowns in these same runs report abs_nz = 0.99999–1.00000 with C-GROUND-LOCK ENGAGED. The two populations are 1.00000 versus 0.00027 — kAxisTolerance could be 0.9 or 0.05 and nothing would change. And lock_enabled was 1 throughout while gate A never rejected the contact, so both are exonerated: the fix belongs at is_ground_normal and nowhere else.

What this result does not cover

Seeds 1 and 2 were captured without timestamps — the collector used plain docker logs -f — so their lines cannot be placed in the descent window and only seed 3 is quoted as the measurement. Timestamps belong in the probe’s own output, not in how it happens to be captured. And the probe prints the normal, not the actor that owns it, so the geometry supplying it is still unnamed.

07 The run destroyed the evidence it was chasing

Two correct rules, one trap

Re-flying citysample-sensors seed 1 overwrote the 2026-08-27 failing run — trace, result JSON, chase video, MCAP bag — the files SIM-27 names as its freshest evidence. Nothing malfunctioned: run_scenario.py clears those paths up-front on purpose, because a stale file reported as this run’s evidence is worse than none, and the tag is <scenario>-seed<N> so artifacts stay traceable. Combined, they mean the best evidence for a defect sits exactly where the next reproduction attempt deletes it — and the more the run matters, the more likely that seed is re-flown. Filed as SIM-41.

Salvaged: 427 samples to t = 85.06 s, dz = 1.71 m, a by-product of replaying the original while building the step-2 detector. The ~760 samples carrying the split out to 107.9 m are lost. Every number quoted from that run predates the loss and still stands.

A rate correction that changes the plan

This session said the split was “~1 in 10 per seed”. That is the Blocks figure — 1.7%, a world where the fault essentially cannot occur. On CitySample the ticket records a 10-seed gate splitting on 9 of 10, and 7 of those traces trip the step-2 detector on replay: 70–90% per seed. Tonight’s clean landing is the minority outcome. So the next run is three seeds under distinct tags, not ten — ~97% odds of catching a failure, and distinct tags are what stops it repeating the loss above.

08 Where step 1 stands

Done. The claim the ticket carried for three weeks — that ground is inferred from a collision normal and a coarse proxy defeats it — is now a measurement rather than a reading of source. Step 3 keeps the shape it already had (trace downward; blocking geometry a few cm below plus slow descent ⇒ ground-lock), with two constraints the data adds: do not touch kAxisTolerance, and change nothing outside the is_ground_normal decision.

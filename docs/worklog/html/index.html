2026-08-16 · SIM-32

The Ground That Was Not There

The gate that stops the vehicle falling during bring-up rather than repairing the fall afterwards. The first cut asked IsStreamingCompleted(nullptr) — "is the whole world settled" — which on CitySample never went true, so every bring-up paid the full 300 s ceiling. Scoping the query to the cells under the vehicle fixed that: a verdict in 0.4 s. And 0.4 s is the wrong answer. The on-screen log named the mechanism — Collision#2 with FastGeoSurrogateActor_0 — the vehicle had come to rest on the far-field surrogate, whose cells are legitimately Activated, so the query answers truthfully about a world that is complete for the detail level requested at that instant. Five minutes later the real city replaced the surrogate, the support vanished, and the vehicle fell 32 m before landing on the actual ground. Instrumenting the query every tick for 600 s then killed the obvious fix: one transition, TRUE at 0.400 s and never FALSE again — straight through the swap — so a dwell requirement cannot help, because dwell only helps if the signal changes. IsStreamingCompleted has no notion of “the ground under me is the ground that will still be here in a minute”. A negative result about the predicate, not the gate. Parked — SIM-30’s pause-and-probe is the official solution for now, with the leading hypothesis for a revisit written down: CitySample lives on a spinning disk, and while slow storage doesn’t cause the predicate bug it sets its blast radius — on NVMe the gap the vehicle falls through should shrink with the load time. Also demonstrated rather than predicted: holding physics starves PX4's HIL stream — 166 poll timeout errors and no finite EKF origin — so SIM-10 is not a separate task. And a trap walked into by being careful: the plugin backup put a second AirSim.uplugin inside UE's recursive scan root.

2026-08-14 · SIM-31 · III

GPS Waypoints, Without The Controller

The last of the five capabilities, and the one the design called "the only piece needing controller changes". It didn't. PX4 has no global setpoint message, so a lat/lon must become a local coordinate somewhere — but "somewhere" only has to be before the setpoints start, and run_scenario.py is already there. Everything turns on which reference the conversion uses: AirSim's declared OriginGeopoint and PX4's EKF ref_* sit 13.8 m apart, so converting against the wrong one puts every waypoint ~14 m off on a stack where nothing is broken. The maths is PX4's own azimuthal equidistant projection on its own sphere constant — a more accurate ellipsoid would be worse, because the target frame is PX4's. Tested as a round trip: the scenario's GPS waypoints are generated by inverting the projection on a known 10 m square, so the conversion has to give the square back. It did, exactly, and flew 4/4 with errors indistinguishable from the same square declared in ENU.

no controller change round trip exact wrong reference = 14 m all 5 capabilities in

A scenario could say where to fly and how tightly to score it — not how fast the aircraft may fly getting there. Capping horizontal speed to 0.5 m/s cut waypoint error from 0.76 m to 0.06 m on the same seed, which says the baseline's error is largely approach speed rather than controller quality — and every gate number this project has quoted was measured at 12 m/s. 2026-08-13 · SIM-29

The Chase Recorder Captured QGroundControl

Wiring the chase capture into run_scenario.py was meant to be plumbing. Then the regression test — a headless stack, which should record nothing — produced an 8.2 MB mp4. DISPLAY=:99 inside the renderer was resolving to QGroundControl's X server. Every container here shares one network namespace, and an X server binds an abstract unix socket that Linux scopes to the netns, not the filesystem — so a display number is stack-global, and qgc-entrypoint.sh:9 has owned :99 since the Gazebo era. The renderer had no Xvfb process and an empty /tmp/.X11-unix, and xdpyinfo answered anyway. The saved artifact showed QGC mid-flight — "Flying / Offboard", 20.0 m, the vehicle tracking across a satellite map: a recording of a real flight, correctly timed, of entirely the wrong thing. The guard written the day before had anticipated a black rectangle, which is the benign version — a black frame reads as broken, a map reads as evidence. Fixed twice over: the renderer moved to :77, and both callers now require a local Xvfb process, because on a shared netns "a display answers" never meant "the display is ours".

recorded the wrong window abstract sockets are netns-scoped :99 belonged to QGC 7 flights, 4/4 each

Folding The Capture Into The Engine Image

The previous entry proved the chase camera can be recorded, using a throwaway image built outside the repo. One question retired it: "what if we just add the new packages to the unreal container?" The probe was carrying two separate confusions — it never needed its own container (the capture already ran inside sim-unreal), and it needed its own image only because five packages were missing. xvfb, ffmpeg and x11-utils now sit in the engine image's late root-only apt layer: 178 MB on a 57.4 GB base, 34 s to rebuild, with the pinned-by-digest engine untouched. Xvfb turns out not to be separable at all — Unreal resolves DISPLAY at process start — and the 4.2% encoder cost removes any reason to split ffmpeg out either. The layer asserts that an X server runs, not that a binary exists. Running it found two bugs, both in the harness rather than the feature, both the same shape: "is the file growing" fails on a healthy capture (x264 buffers; a parked drone compresses to nothing — 48 B for four seconds, then 524 KB), and the stop path ran ffprobe on a host path from inside the container, printing ? for every number while the 63 MB recording was perfectly fine.

2026-08-13 · SIM-29 · I

Recording The Chase Camera By Giving The Engine A Screen

The question was whether the chase camera could be recorded in high resolution. It was mis-framed: resolution was never the constraint. The chase view is AirSimCameraDirector, which has no RPC binding at all — simGetImages serves vehicle-mounted cameras only — and that path is capped near 13–14 Hz at any resolution by a blocking GPU→CPU readback whose fixed ~71 ms term dominates. Meanwhile ViewMode defaults to FlyWithMe, so the chase camera has been running on every run this project has ever done, rendered to nothing because sim_up.sh launches with -RenderOffScreen. Give the engine an Xvfb display instead and ffmpeg -f x11grab records it at ~31 fps at 1080p, with the drone in frame, changing nothing in Cosys-AirSim. One trap inside the measurement: x11grab re-emits the last frame when the screen is unchanged, so it always reports the rate you asked for — the first "60 fps" was the grab clock, not the engine, and only mpdecimate tells the truth. A no-encoder control run puts x264's cost at 1.3 fps, 4.2%, which is what makes ~31 fps a render ceiling rather than contention.

~31 fps vs ~13–14 Hz chase camera was always on grab rate ≠ render rate no plugin change
2026-08-13 · SIM-28

The Vehicle Falls 80 m On Every Boot

Supersedes a conclusion in yesterday's entry. That one recorded a stale EKF origin on 40 of 40 bring-ups by a systematic 9.13 m and argued — in bold — that 57 mm of spread across 40 samples made it "systematic, not a race". Wrong: a tight distribution can mean deterministic timing just as easily as constant offset, and the two are only separable by watching the quantity move. Sampling sensor_gps from the first PX4 boot shows the vehicle falling 118 → 114 → 108 → … → 41 m at ~5 m per sample before snapping back to its spawn altitude — the vehicle genuinely falls ~80 m during bring-up, and PX4 latches its origin on the second sample of that fall. So 9.13 m was never an offset anyone chose; it is the gap between where the fall had reached and where the vehicle ended up. The earlier decomposition into −7.85 and +1.87 was arithmetic on a moving target. Same family as SIM-21. Also: the Blocks floor is not at Z=0 (it is 0.9 m below), and PX4 latches from GPS, not the barometer.

2026-08-08 · SIM-23

A Frame That Was Never Read

The renderer had been dying mid-flight since 2026-08-02 — 13 of 18 crash reports, one bug — and the report stated the cause outright in a line nobody had read closely enough: into an array of size 0. The out-of-bounds index is not the bug; every recorded index is a legal offset into resolution². The array is empty, because ServiceAsyncCapture discards the bool that ReadPixels returns and advertises readiness anyway, handing AirSim's physics thread a zero-length TArray. The obvious data-race reading was refuted by the sizes: a reallocation under a live reader gives varied nonzero sizes, and all eleven say 0. Verified by fault injection, since waiting on a daily fault is not evidence — upstream + one emptied buffer died in 20 ms with the exact production signature; with 0006 it logged the size and flew on. A 90-minute soak then ran 45 consecutive flights past the historical 57-minute failure point with zero crashes — labelled as absence evidence, since no fault fired naturally. Chasing the build route found a second gap: 0005 had never reached Blocks either, five days after it landed. Also closes the "uncharacterised" instability open since 08-03 — same bug, chased down the wrong array, by a soak that only ever drove the image path.

13 of 18 crashes array of size 0 A/B: dead in 20 ms vs alive 90-min soak, 45/45 flights 0005 missing from Blocks

§ 2 · CONVENTION

About these logs

Standing rule

A worklog is a running record, not a final report. Findings, numbers, decisions, and dead ends are appended as they happen, so a resumed session — or a human — can pick up exactly where the work stopped, with the evidence intact.

  • Standalone. Each entry carries its own findings in full — never a "see other doc" pointer.
  • Honest. What failed, what was abandoned, and what remains unverified are recorded alongside what worked.
  • Sourced. Repo facts cite file:line; sim results cite the command and its output; external claims cite the URL or issue.
  • Rendered. Every Markdown worklog has a companion page here, hand-authored and self-contained, with at least one diagram built only from the log's real content.

Markdown sources live in docs/worklog/; these renders live in docs/worklog/html/. The backlog they feed is docs/todo.md.

02 Five failures, four already in this repo's notes

1 · The renderer could not start — Vulkan ICD path mismatch

LogVulkanRHI: Error: vpCreateInstance(...) failed, VkResult=-9   (INCOMPATIBLE_DRIVER)
exit 139   (SIGSEGV)

Asked the loader directly rather than guessing, and it said so plainly:

ERROR: [Loader Message] /usr/lib64/libGLX_nvidia.so.0: cannot open shared object file
ICD filelibrary_pathapi
nvidia_icd.jsonlibGLX_nvidia.so.01.3.204.1
nvidia_icd.x86_64.json (CDI-injected)/usr/lib64/libGLX_nvidia.so.01.4.341

The host is Bazzite (Fedora-family), so its CDI spec names the Fedora path; this container is Ubuntu, where the driver lives under multiarch. A symlink in docker/lane-c.Dockerfile fixes it — vulkaninfo shows zero usable devices before, RTX 3080 / DISCRETE_GPU / 1.4.341 / driver 610.43.03 after.

This is a PATH mismatch, not the too-new-driver incompatibility that deferred Lane B. 610.43.03 works fine once the loader can find it. Worth stating clearly, because the superficial resemblance to P0-09 invites the wrong conclusion.

2 · --settings /path silently became a map name

LogUObjectGlobals: Warning: LoadPackage can't find package /settings.json.
LogLoad: Error: Failed to enter /settings.json

Unreal took the space-separated argument as a level to load. SimHUD.cpp:369 documents the real form: -settings= — single dash, =-joined. With it, listVehicles returns ['PX4'] rather than the default ['SimpleFlight'], which is how you can tell the file was read at all.

3 · "Port 41451 is bound" was not evidence of anything

I reported the host port as proof AirSim was up. It was not: docker -p makes the host listen via docker-proxy immediately, whether or not anything inside the container is. The connection reset gave it away. Real evidence is an RPC response:

getServerVersion -> 4      ping -> True      listVehicles -> ['PX4']

Note getServerVersion returning 4 against the client minimum of 4 — the same handshake that failed against CARLA, which reported version 1.

4 & 5 · Silent /fmu/out/* — both causes already documented here

D-02 · shared netns is not enough

Fast-DDS discovers over UDP but delivers over shared memory, and each container has its own /dev/shm. Docker confirmed it with the exact error D-02 records: failed to join IPC namespace: non-shareable IPC.

P1-02 · BEST_EFFORT publishers

A default RELIABLE subscription matches nothing and sees zero messages on a healthy stack — so ros2 topic hz without a QoS override was never a valid probe.

/fmu/out/sensor_combined         DATA
/fmu/out/timesync_status         DATA

sim clock: +5016 ms over ~4 s wall

Four of the five failures were already written down in this repo. Lane A's lessons transferred to Lane C essentially unchanged — a concrete argument that keeping Lane A alive as the reference was right.

03 Two findings that outlive this task

Lane A and Lane C collide on ports

Lane A publishes 4560, 8888, 14540, 14550, 18570 — exactly what Lane C needs. Found via Bind for 127.0.0.1:4560 failed: port is already allocated when the flight gate had left Lane A running.

They cannot both run with published host ports on this box, so the parity diff had to be captured sequentially. That bites C-07, whose whole purpose is comparing a Lane C run against a Lane A baseline. Either give them distinct ROS_DOMAIN_IDs and non-overlapping ports, or accept sequential comparison and say so.

The DDC does not survive container recreation

First launch spent ~3 minutes compiling shaders; the cache lives in the container's writable layer, so docker rm threw it away. A named volume at /home/ue4/.config/Epic cut startup to 9 seconds.

04 A deliberate divergence from upstream

Upstream's PX4 example sets NAV_RCL_ACT=0 and NAV_DLL_ACT=0, disabling the RC-loss and datalink-loss failsafes. Not done here.

Lane A leaves the GCS-datalink check enforced and satisfies it with a real QGroundControl service, because PX4 refusing to arm without a datalink is a property of the real aircraft too. Disabling it in Lane C would make the lanes diverge exactly where sim-to-real parity matters, and hide an arming failure the real Pixhawk 6C would still have.

Consequence: arming in Lane C will need a datalink the same way Lane A does. Intended, not an oversight.

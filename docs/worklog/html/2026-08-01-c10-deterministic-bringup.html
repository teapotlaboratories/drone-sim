and a Check That Nearly Lied

The stale origin above is not a replay of C-09’s 35.167 m — it is 9.069 m, from a fresh race. The failure is genuinely order-dependent and recurs at a different magnitude each time, which is why a fixed workaround would not have held and why the check has to be a measurement. The retry path executed for real — the part of error handling that usually ships untested.

02 The settle-wait was necessary but not sufficient

The script waits for AirSim’s ground-truth z to hold still before starting PX4. That was not enough on its own — the origin still came up 9 m stale. What saves the run is the verify-then-restart loop after the fact. So the honest description is “verify and repair”, not “order it correctly”. Recorded because the tempting write-up would be a claim the evidence does not support — and would invite the next person to delete the retry loop as redundant.

03 The check reported OK on a NaN

First cold start printed:

OK: EKF origin sane: ref_alt nan m vs GPS 123.280 m = nan m apart (tolerance 1 m)

abs(nan - 123.28) is nan, and nan > 1.0 is False, so the comparison fell straight through to “sane”. PX4 publishes ref_alt as NaN until the EKF has established an origin at all — so the single most dangerous state, no origin whatsoever, was the one state the check green-lit.

This repo already had test_nan_error_must_not_pass in the gate tests, for the same class of bug in the same kind of numeric guard. I did not apply the lesson to new code. Now guarded explicitly, with a regression test carrying the observed string, and the exit code distinguishes UNKNOWN (no origin yet — wait and retry) from STALE (ordering already wrong — restart).

wait_for_fmu had the same defect independently: it treated any published ref_alt as “telemetry ready”, NaN included. It now requires a finite value.

A checker that passes on garbage is worse than no checker, because it converts “unknown” into “verified”. Same class as the Dockerfile layer that recorded empty versions while the build succeeded, and the capture overlay that silently printed ... for a whole video.

04 Why VOID and not FAIL

A run against a mis-initialised origin must be void, not failed. Scoring it would blame the flight code for a bring-up defect — and that flight code is byte-identical to the one scoring 10/10 in Lane A. Poisoning a success-rate gate with void runs makes the gate actively misleading. Same distinction P1-08 draws for Lane A, now built for Lane C.

05 Configuration recovered from evidence, not docs

The container invocations existed nowhere in the repo — only in worklog prose. They were recovered with docker inspect from the stack that had just flown 4/4, so the script reproduces something observed working rather than something the docs describe.

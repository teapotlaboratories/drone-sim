01 Why seven fixes all missed

The thread arrived here with a negative result: the SCS_FinalToneCurveHDR → SCS_FinalColorLDR patch was built, deployed, verified by md5, and did not change the washout. That retired the hypothesis the whole investigation rested on and left the mechanism unknown.

Seven interventions had failed by then — six world-side (a scalability .ini, SM5→SM6, the UE4→UE5 package conversion, AtmosphericFog→SkyAtmosphere) and one plugin-side (the capture source). Every one targeted the world or the output encoding.

What the accumulated failures were actually saying

None of them targeted how the capture component itself is configured. If the world renders correctly in Unreal's own screenshot and incorrectly through simGetImages, in the same process on the same frame, the difference has to live in the component doing the capturing. So this session started by reading the vendor source rather than proposing an eighth fix.

02 Reading the source instead of guessing

Grepping PIPCamera.cpp for the capture setup killed the leading hypothesis immediately and turned up two better ones.

Killed on sight — bAlwaysPersistRenderingState

Expected to be false (the UE default), which would discard temporal history every capture and break auto-exposure, TSR and Lumen accumulation. It is explicitly true at PIPCamera.cpp:459. Not the cause; cost nothing to rule out. (This dismissal turns out to be too broad — see §08.)

Candidate 1 — a gamma applied to the Scene camera and nothing else

AirSimSettings.hpp:170    static constexpr float kSceneTargetGamma = 1.4f;
AirSimSettings.hpp:1526   capture_setting.target_gamma = settings_json.getFloat("TargetGamma",
AirSimSettings.hpp:1527       capture_setting.image_type == 0 ? CaptureSetting::kSceneTargetGamma : Utils::nan<float>());
PIPCamera.cpp:747-748     if (!std::isnan(setting.target_gamma))
                             render_target->TargetGamma = setting.target_gamma;

ImageType 0 is Scene. Every other image type gets NaN and leaves the render target's gamma alone. So Scene — and only Scene — gets gamma 1.4 on top of an already tone-curved image, which lifts midtones. That is a milky wash, and it would explain why the defect is specific to the one image type anyone looks at.

Candidate 2 — Lumen explicitly turned OFF for the capture

AirSimSettings.hpp:217-218   bool lumen_gi_enabled = false;
                             bool lumen_reflections_enabled = false;
PIPCamera.cpp:701-715        if (capture_setting.lumen_gi_enabled) { ... Lumen ... }
                             else { bOverride_DynamicGlobalIlluminationMethod = 1;
                                    DynamicGlobalIlluminationMethod = ::None; }
                             (same shape for ReflectionMethod)
The else branch is the load-bearing part

When the setting is false the code does not simply leave the capture alone — it overrides global illumination and reflections to None. City Park is authored for Lumen and Unreal's own render uses it, so the AirSim capture had been rendering with GI and reflections disabled the entire time. Missing GI reads exactly as flat, ambient-only, hazy lighting.

Both are settings.json keys — TargetGamma, LumenGIEnable, LumenReflectionEnable (note upstream's typo in the neighbouring LumenSceneLightningDetail, which must be matched exactly). No plugin rebuild is needed to test either, the first time in this thread an experiment was cheap.

03 The rig voided its own premise

The first run crashed the simulator at startup, and the crash log carried something far more important than the crash:

LogPluginManager: Warning: The same version (v3) of plugin 'AirSim' exists at
  'AirSim.bak.1785739115/AirSim.uplugin' and 'AirSim/AirSim.uplugin'
  - second location will be ignored

Unreal's plugin manager walks Plugins/ recursively and de-duplicates by name+version, keeping one location and ignoring the rest. The world had four copies, because inject_airsim.py --force moved the previous plugin aside to Plugins/AirSim.bak.<ts> — a sibling inside the scanned directory.

Locationmd5BuildEngine verdict
Plugins/AirSim.bak.17857391152122e037stock upstreamKEPT
Plugins/AirSim1599713eLDR-patchedIGNORED
So the previous day's negative result is void

The LDR patch was never loaded. The md5 check that "verified" it examined the right file and answered the wrong question: what sat on disk at Plugins/AirSim, not what the engine resolved. The companion check — strings | grep -c FinalToneCurve returning 0 — proved nothing either: it returns 0 on the stock build too, because those enum names are not stored as strings.

This is a defect in the injector shipped in PR #33. Fixed three ways: backups now go to <project>/AirSimBackups/, outside Plugins/; shadowing_plugin_copies() refuses to finish an injection that would leave a second copy; and five regression tests cover it, including the case that matters — a backup outside Plugins/ must not be flagged.

The crash itself was also self-inflicted: a camera declared without explicit X/Y/Z/Pitch/Roll/Yaw keeps AirSim's NaN sentinels and reaches FRotator::Quaternion as P=nan Y=nan R=nan, taking the simulator down in BeginPlay. Not a validation error — a SIGSEGV.

04 The 2×2: gamma refuted, Lumen real

Run against the stock upstream plugin (2122e037), so any fix found applies to vanilla Cosys-AirSim rather than to a patched tree.

TargetGamma is refuted — a clean negative from a proper factorial. 1.4 → 1.0 moves the image by −0.4 range, i.e. noise. The setting is real and is applied, but the render target's gamma does not reach this output path. Lumen is real: +16.4 range, +2.9 std, and the combined cell adds nothing over Lumen alone, so the two factors do not interact.

05 Altitude, and the fog nobody looked for

Both frames were still badly washed, and both still carried the out-of-focus concrete border that means the camera is inside geometry. Capture settings are parsed at startup but pose is free over RPC, so one simulator run can walk many positions.

The washout scales with altitude

Mean climbs monotonically to near-white (242.3 at 300 m), contrast collapses to 68, and the black point rises from 53 to 184 — darks lifted toward one bright colour. That is atmospheric fog / aerial perspective, a property of the world. It also retro-explains the original side-by-side "proof" that AirSim renders worse than Unreal: those two frames were taken from different viewpoints, a caveat recorded at the time and then reasoned past.

06 A bug in the measuring instrument

The sweep left a cyan cast that no hypothesis explained, so the client was checked against AirSim's own PNG encoder on an identical frame (scripts/_check_channel_order.py):

raw  as-BGR  B= 183.53 G= 178.21 R= 158.47
png  (BGR)   B= 158.47 G= 178.21 R= 183.53
mean|raw - png|         = 19.59
mean|raw_swapped - png| =  0.00      ← exact
Cosys-AirSim returns the uncompressed buffer as RGB, not BGR

Reading it as BGR swaps red and blue — which does not look like a bug, it looks like a plausible cyan colour cast, and was read as one for a full day. Every PNG saved in this investigation had red and blue swapped. Fixed, along with the luminance weights, which were applying 0.299/0.114 to the wrong channels.

Three problems, one symptom

1 — colour cast
CLIENT
RGB read as BGR. Affects saved images only, never the simulator.
2 — veiling haze
GEOMETRY
Camera inside the world; a near surface blurred by depth-of-field is a film over everything behind it.
3 — flat lighting
LUMEN OFF
GI and reflections forced to None in a world authored for Lumen.

With all three addressed, at z = −10 m contrast went 143.98 → 197.8 and the frame reads as a park — blue sky, white cloud, green foliage, the lake, a car on the road (out/lane-c/capture-exp/before_after.png). The residual brightness (mean 191, p99 pinned at 251) is the sky blowing out on a bright day — an exposure-tuning question (AutoExposureCompensation), not a defect.

07 AirSim vs Unreal, same pose

Everything above explained the gap without measuring it, and this thread had twice mistaken one for the other. Making the comparison apples-to-apples turns on one line:

SimModeBase.cpp:2120  CameraDirector->initializeForBeginPlay(..., getCamera("fpv"), ...)

The viewport's FPV camera is the PIPCamera literally named "fpv" — which is why earlier attempts comparing the viewport against front_center were comparing two different cameras, and why "FPV ≠ front_center" looked like a mystery.

Both captures are issued inside a single pose-holding loop, so the vehicle cannot drift between them. HighResShot letterboxes to the viewport aspect, so the bars are cropped before scoring — left in, they would manufacture the very difference being measured.

08 The residual: aliasing, and a metric that lies

Re-run at 1920×1080, tone agreement is tighter still — worst |Δmean| is 1.15. But AirSim's frames carry hard aliased leaf edges with red/blue colour fringing where the native render is cleanly resolved.

The mechanism is in the source, and it is deliberate

PIPCamera.cpp:186-188  //We set all cameras to start as nodisplay
                       //This improves performance because the capture components are no longer
                       //updating every frame and only update while requesting an image
PIPCamera.cpp:455-459  setCaptureUpdate(capture, nodisplay)
                           capture->bCaptureEveryFrame = !nodisplay;
                           capture->bAlwaysPersistRenderingState = true;

Every camera starts as nodisplay, so bCaptureEveryFrame is false and the capture renders one shot per simGetImages. The history buffer survives — but with no per-frame captures nothing accumulates into it, so TSR/TAA never converges. The viewport, rendering continuously, does. That is the entire difference — and it means the §02 dismissal of bAlwaysPersistRenderingState correctly ruled out one failure mode and was then wrongly treated as ruling out the temporal path entirely.

One further check: showToScreen() (PIPCamera.cpp:406) touches only the cine-camera component, never the scene captures — so running in Fpv view mode does not enable per-frame capture, which is why the aliasing survived the vs-native run.

Stock levers, priced

FXAA is a trap in the ratio metric

Its ratio looked best of everything (2.04× vs 2.94×) purely because it degraded the native reference too (hf 7.04 → 10.36) — FXAA is worse than TSR. AirSim's own noise went slightly up. Ratios are only meaningful when the denominator holds still; the absolute column is the one to read.

What ForceUpdate is actually fixing

 Lumen onLumen off
baseline20.7117.56
ForceUpdate17.8317.61

Lumen costs +3.15 of noise and ForceUpdate recovers essentially all of it. With Lumen off, ForceUpdate does nothing. So it is denoising stochastic Lumen GI sampling, via the temporal accumulation that per-frame capture finally makes possible — the two settings belong together.

An honest limit on the metric

A residual ~17.6 vs native ~7.0 survives every lever — not Lumen, not temporal, and tellingly not meaningfully reduced by 2× supersampling. Genuine geometric edge aliasing would have collapsed under a box filter. That points at a large part of this "2.5×" being native's TSR softening the reference rather than AirSim adding noise: |image − median3| cannot distinguish speckle from sharpness, and the native frame is measurably blurrier. It also undercuts a number reported above — AirSim's apparent contrast advantage at 1080p (+6.6 to +13.8) is most likely its own speckle widening the p01–p99 spread. Deferred as C-12, where the first task is a better metric, not a better fix.

09 What it costs on the real graph

The fix was validated on one camera at 1080p in a standalone simulator. Lane C runs two cameras plus a GPU-LiDAR at 640×480, and ForceUpdate renders every enabled camera every frame — so the cost scales with the graph, not with the setting (scripts/measure_lane_c_rates.sh, Blocks).

ConfigRGBDepthLiDARIMU
stock settings18.7 Hz18.1 Hz10.0 Hz333 Hz
+ Lumen GI/reflections17.3 Hz16.8 Hz9.9 Hz333 Hz
+ ForceUpdate17.1 Hz16.6 Hz9.0 Hz333 Hz

Lumen costs ~7% of RGB; ForceUpdate ~1% more on RGB but ~9% on LiDAR. Total ~8.6% RGB and ~10% LiDAR for the image quality. All 14 sensor checks pass.

Correction — the 31 Hz claim is retired, and nothing regressed

Stock settings on the same grey-box world now measure 18.7 / 18.1 / 10.0 Hz, not the recorded 31 / 29.6 / 17.4. The old figure predates lane_c_perception.launch.py, which pins update_airsim_img_response_every_n_sec = 0.05 (20 Hz) and update_gpulidar_every_n_sec = 0.1 (10 Hz) — so 18.7 Hz is 94% of its ceiling and the LiDAR sits exactly on target. That same file records the measured Scene+Depth RPC ceiling as ~21.7 Hz, so 31 Hz was never sustainable. The clearest tell is the LiDAR: 17.4 Hz from a sensor configured RotationsPerSecond: 10 was reporting poll rate, not data rate. The old number was measuring the wrong thing.

10 Still open

  • Spawn placement remains unfixed (C-13). z = −10 was found by sweeping, not derived; an arbitrary world has no obligation to put usable ground at the origin. Four investigations in this thread were confounded by it.
  • The aliasing residual (C-12) — deferred, and the metric is the first thing to fix, not the rendering.
  • The LDR patch has still never run. Moved to patches/cosys-airsim/experimental/, excluded from the applied set. If it is ever revisited, re-test TargetGamma with it: gamma came back a clean null on stock, which is odd for a setting genuinely applied at PIPCamera.cpp:747, and plausibly because the HDR capture source bypasses the render target's gamma encode. The "gamma is refuted" finding is strictly a stock-HDR result.

What shipped

Three keys in sim/ue5/settings.json, on a stock plugin binary — the only applied patches (0001–0003) touch ros2/src/airsim_ros_pkgs/, not the UE plugin:

"LumenGIEnable": true, "LumenReflectionEnable": true, "ForceUpdate": true

Method note. Every conclusion here that survived came from a control, and three that did not survive were killed by one: the gamma null (factorial), the FXAA "win" (absolute vs ratio), and the ForceUpdate frame-rate scare (stock baseline was already 18.7 Hz). The recurring failure mode in this thread was not bad hypotheses — it was measuring one thing and attributing it to another.

Worth saying plainly

The baseline's ~0.76 m error is largely approach speed, not controller quality. Every gate number this project has quoted was measured at 12 m/s.

02 The envelope and the time budget are one decision

At the baseline's state_timeout_s: 60 the slow run failed 3 of 4 with timeout in state waypoints — while tracking beautifully. The budget covers the whole sequence, and 40 m at 0.5 m/s needs ~88 s of flying. Nothing was wrong with the aircraft; the scenario had not been given time to be slow in.

Limits live in PX4, not in our controller: offboard_control sends position setpoints and PX4's position controller turns those into velocity and acceleration. A limit enforced on our side would be one the autopilot does not know about.

03 The review’s first finding: the gate could not run

The lesson, not the patch

The gate is the thing that scores this project, and it had been broken by a change that never touched it. The parameter is now keyword-only, so the same mistake cannot recur positionally.

Five more were real: a harness fault was being scored as a flight failure (a misspelled limit key would have reported "SR 0%, control failure" for runs that never left the ground); limits leaked across runs on a reused stack, so the baseline would have flown at 0.5 m/s while recording applied_limits: null; a stopped PX4 read as a missing parameter; an origin-only run rewrote a declared vehicle pose back to the PlayerStart; and omitting altitude_m would have moved the world 122 m, because AirSim overrides only the keys present.

04 The finding that undermined the central claim

The applier was built on “read it back, because px4-param set on an unknown name is not an error”. True — but a read-back proves the value is stored, not that PX4 considers it legal. param set neither clamps nor rejects.

MPC_XY_CRUISE   min=3.0   max=20.0   default=5.0     # and we were writing 0.5

The read-back dutifully “confirmed” a number PX4 itself treats as out of range. Two changes: validate against parameters.json, which ships inside the image and is the authority; and drop MPC_XY_CRUISE entirely, since MPC_XY_VEL_MAX is the cap that acts on offboard position setpoints. Re-flown after: errors 0.063 / 0.063 / 0.058 / 0.056, unchanged. It had never been the operative limit.

A GPS waypoint converted against OriginGeopoint instead of ref_lat/ref_lon would land ~14 m off — an error shaped exactly like a control bug. The design asserted this; it is a measurement now.

Unexplained, and recorded as such

What the 13.4 m east is made of — level offset from the world origin, GPS init bias, or both — is not known. Slice three depends on knowing, so it is written down rather than rounded away.

Verification

  • Flight gate, 2 seeds, Blocks: 2/2, 100% — the critical break, gone.
  • CitySample square-10m-slow: 4/4, envelope printed, read back and recorded.
  • Blocks with a declared origin and 45° yaw: 4/4, origin confirmed in the run-time settings and in PX4's own ref_lat/ref_lon.
  • Negative tests: unknown limit key refused; accel_horizontal_mps2: 1.0 refused against MPC_ACC_HOR's declared minimum of 2.0; origin-only run leaves a declared pose at 10/20/-50.
Still open

GPS waypoints — the slice that touches the controller. Five of the six limit keys have never been flown, only set and read back. And the 13.4 m.

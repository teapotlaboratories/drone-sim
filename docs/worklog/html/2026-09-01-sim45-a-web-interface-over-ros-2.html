02 The transport choice, and what it cost

Two options went to the owner. A purpose-built HTTP+SSE server with a hard-coded two-command allowlist would have needed no new dependency and would have been narrow by construction. The owner chose rosbridge_suite — the right call against this project’s primary rule, reuse upstream rather than reinvent.

The trade is worth stating plainly, because it is the whole shape of the work that followed: the cost moved from write a transport to make a deliberately general bridge obey hard stop 1. rosbridge exists to expose an entire ROS graph to a browser. That is precisely the wrong default for a page with a take off button on it.

What the choice bought

It also made the design better in a way the narrow option would not have. Once the browser speaks ROS 2 for everything, the chase camera has to become a ROS topic too — and solving that turned out to remove a risk rather than add one. record_chase.sh, which the gate depends on, is left completely untouched.

The publish allowlist is real, and it has three traps

rosbridge_library/capabilities/publish.py checks topics_pub_glob before it creates the topic registration and returns silently on no match. So the enforcement point exists. Reading rosbridge_websocket.py at the same time turned up three properties that a page could depend on wrongly — each of which produces something that looks locked down and is not:

PropertyWhat getting it wrong looks like
The globs are strings containing a list literal, not string arraysA parameter type error at best; an unfiltered bridge at worst.
parse_glob_string("") returns None, and None means no checking at allSecurity is opt-in. A glob left off opens the bridge rather than closing it — the failure is silent and inverted.
topics_pub_glob and topics_sub_glob are independentUsing the legacy single topics_glob applies one list to both directions — and the read set must be wide while the write set must be exactly one topic.

The chase camera can be a ROS topic after all

An X server binds an abstract unix socket, and Linux scopes abstract sockets to the network namespace — which every container in this stack shares. This repo has already paid for that fact once, from the other direction: sim_up.sh:75 records :99 resolving to QGroundControl’s Xvfb, after which the chase recorder cheerfully filmed a map view and wrote it out as evidence.

Probed with two throwaway containers sharing one netns — which is exactly sim-ros2’s position relative to the renderer:

abstract socket   @/tmp/.X11-unix/X77 from the second container        : CONNECTED
ffmpeg -f x11grab -i :77 -frames:v 5 -f mpjpeg                         : 5 JPEG frames, 8270 B

The probe also logged Cannot get the image data … major_code:130 (MIT-SHM) and fell back to a plain read — because the probe shared only the network namespace. The real stack shares IPC as well, so the shared-memory path is available there. The fallback working either way is the useful half.

04 Narrowing a bridge built to be wide

Four measures, in the order they take effect:

  1. topics_pub_glob = ['/mission/command']. One topic, and it is subscribed only by offboard_control with manual:=true — so even that single permission is inert during a gate run.
  2. services_glob = "[]" and actions_glob = "[]". Without these the page could call any node’s set_parameters and retune takeoff_altitude mid-flight. "[]" is an empty allowlist, which is not the same as "". rosbridge appends /rosapi/* to a non-None services glob by itself, so roslibjs still resolves topic types.
  3. Bound to loopback. Under NET_MODE=host the container namespace is the host’s, so the bind address is the only thing keeping the buttons off the VPN — the exposure sim_up.sh:104 already records for MAVLink port 14540.
  4. A proof-of-sim interlock in offboard_control, not in the transport. It refuses every take-off unless AirSim’s RPC answers.
Why the interlock is a positive proof, and why it is not in the web layer

The tempting version is “refuse if it looks like hardware” — no /dev/ttyACM0, a particular SYS_AUTOSTART, a hostname. Every one of those fails open: an unrecognised setup passes, so the check is weakest exactly where it is least understood. Asking instead whether a simulator answers fails closed.

And at the node that actually sends VEHICLE_CMD_COMPONENT_ARM_DISARM it guards every route to /mission/command. Put in the web layer it would have guarded the browser and nothing else — ros2 topic pub walks straight past it, which is the lower path in the diagram above.

05 What was built

offboard_control gained a mode, not a sibling: a manual parameter, default false, two states, one subscription. TAKE OFF walks IDLE → STREAM_SETPOINTS → REQUEST_OFFBOARD → ARM → TAKEOFF → HOVER through the existing handlers unchanged. Every existing caller gets byte-identical behaviour.

DecisionWhy
IDLE and HOVER are exempt from the per-state timeout, and nothing else isThe timeout exists so a controller waiting on an arming_state that never arrives cannot hang a CI job for its whole budget. Applied to a state that waits on a human, the same mechanism fails an aircraft for doing exactly what was asked.
A hand-flying session is many sorties: DONE/FAILED publish, then recycle to IDLEThe terminal MissionStatus and the MissionResult go out first, so each sortie leaves the evidence a mission run does. A node that exited after the first landing would leave a page whose buttons silently do nothing.
Commands are validated in the callback and applied in the timerMutating state from the executor thread races every handler in the file, and the symptom is an aircraft that changed state halfway through a tick.
The policy, the allowlist and the MJPEG framing live in modules that import nothingwebui.launch.py and chase_camera.py cannot be imported without a ROS 2 environment, and a test that needs the target can only ever pass on the target. So the tests assert the objects the nodes actually read, rather than a re-expression of them.

32 new tests, all passing, and local CI tier 1 is green. The ones that matter most: the interlock refuses a server that answers with something that is not a msgpack-RPC reply (failing open is the entire risk); the MJPEG splitter keeps a lone trailing 0xFF because it may be the first byte of the next SOI, and dropping it would lose one frame per read forever at a rate nothing would flag; and a test that the launch file still reads the shared allowlist rather than having re-inlined its own copy — which would leave every other assertion passing while describing a module nothing uses.

Nothing has been flown, and no stack has been brought up

That is the part that decides whether any of this works. The image needs rebuilding for rosbridge, web_video_server and ffmpeg. Then: bring up with --display; cross-check every telemetry field against ros2 topic echo, watching for the em dashes the page renders in place of a plausible zero; prove from the browser console that a publish to /fmu/in/vehicle_command is dropped; one hand take-off and landing; a 3-seed citysample-gate1 to show the gate path did not move; and a verified teardown.

The flight needs the owner’s go-ahead for that specific run.

08 SIM-46 — the same day: it becomes a ground station

The owner’s response to SIM-45 landing was “lets make it its own container, faithful to the real thing”. That is a fidelity argument, and it settles a design question rather than reopening one: on real hardware the ROS 2 graph runs on the companion computer and a web page that flies the aircraft does not — it runs on someone’s laptop. sim-qgc has modelled that boundary since the Gazebo era; this is its sibling. It is a safety improvement too: rosbridge is a general ROS-to-websocket bridge, and hosting one on the companion computer is what hard stop 1 is about.

The chase camera cannot move, and the reason is the interesting half

The mechanical reason is that it reads the renderer’s screen through an X abstract socket scoped to the network namespace. The real reason is that a real aircraft has no chase camera. It is simulator scaffolding, in the same family as ground truth, and a ground station that could produce it would be less faithful, not more. So the split is two packages, physical rather than conventional: webui (page, launch, allowlist — no Python nodes at all) and chase_camera.

The container list was the trap, and it was named in advance

sim_up.sh held the list twice — teardown() removed them, the verifier greped a separately written list. A sixth container added to one and not the other gives the worst outcome the script has: a container left running under a teardown that printed “verified”. One STACK_CONTAINERS array now, both consumers derived from it, and a test asserting nothing else in the file names three or more containers.

Three confident wrong theories, then a server log settled it in one line

app.js built its URL with encodeURIComponent(topic), turning /chase/image into %2Fchase%2Fimage. web_video_server does not url-decode that parameter — it hands the raw string to the ROS name validator:

Invalid topic name: topic name must not contain characters other than
alphanumerics, '_', '~', '{', or '}':  '%2Fchase%2Fimage'

And it fails quietly: HTTP 200, the multipart boundary written, connection closed. 22 bytes. The browser sees a successful response and an <img> that never decodes, so the pane is empty — indistinguishable from “no camera is publishing”. What separated them was the same topic answering 22 bytes to the page and 100 frames / 10 s to curl, because curl had been sending raw slashes all along.

One build assertion was wrong, and the build refused it

ffmpeg is a hard Depends: of ros-jazzy-web-video-server and cannot be removed without removing the server the image exists to run. The claim was narrowed to what is true — no AirSim RPC client, no msgpack, no vendored Cosys-AirSim, no chase camera — so the boundary now rests on there being no node there that opens a display, which was the load-bearing part all along. A claim narrowed to what is true is worth more than a stronger one that has to be forced.

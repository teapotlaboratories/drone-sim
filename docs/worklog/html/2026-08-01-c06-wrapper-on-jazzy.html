01 Why this ran before anything expensive

The project chose Jazzy over doc 04's Humble on the reasoning that doc 04's recommendation was inherited from upstream example docs rather than measured. Research then showed upstream itself now documents Jazzy on Ubuntu 24.04 — but also that upstream's CI never builds the ROS 2 wrapper on any distro: its only workflow runs setup.sh, build.sh and MavLinkTest --help, and never invokes colcon. A GitHub issue search for "jazzy" in that repo returns zero results.

So the ordering was the whole point

"Tested with ROS2 Jazzy" was a maintainer assertion with no automated signal behind it. The wrapper is an ordinary ament_cmake package needing no engine, no GPU and no simulator — so it could answer the question for 1m21s. Discovering a distro incompatibility after a 24 GB pull and a multi-hour UE build would have been the most expensive possible ordering of the same two facts.

.repos states at the top that "Versions here MUST agree with versions.lock". A mechanical comparison said otherwise.

The first one reconstructs a broken tree

versions.lock records v2.4.2 as genuinely unbuildable — eProsima deleted the Fast-DDS branch its superbuild pins, so it dies with fatal: invalid reference: 2.12.x. Anyone running vcs import vendor < .repos on a fresh machine checked out the version that cannot compile.

That is exactly the "written from the docs rather than from evidence reproduces a broken stack" failure this project has a rule against — sitting in the file that is the reconstruction mechanism.

Both corrected and re-pinned by SHA, as .repos's own header instructs. And automated: scripts/check_repos_manifest.py now runs in tier-1 CI, verified by restoring the v2.4.2 value and watching it fail.

A caveat about my own first check

The initial find -type f -executable reported "airsim_node NOT FOUND". That was wrong: --symlink-install makes the entry point a symlink, which -type f excludes. The binary was there all along.

Recorded because it is the same shape as the failures this project keeps hitting — the check was broken, not the thing under test — and a less careful reading would have logged a false negative against a perfectly good build.

04 Running it found something nobody was looking for

The node was run with no simulator, expecting it to sit retrying. Instead it said Connected!.

CARLA is UE4-based and the CARLA-Air work (doc 04) reuses the AirSim API, which is why it answers at all. The process is not visible in this container's process table though its socket is — it runs on the host. Both GPUs were near-idle when checked (3080: 111 MiB / 10240; 5060 Ti: 30 MiB / 16311), so it is resident rather than rendering. Not touched — host-side processes need the operator, and killing someone else's simulator to free a port is not a decision to take unasked.

1 · Port conflict awaits C-03

The sim container will try to bind 41451 and lose — or worse, our client talks to CARLA again. Assert what answered, do not trust Connected!. Recorded as coupling airsim-rpc-port-conflict.

2 · Bound to 0.0.0.0

Not loopback — the same exposure class D-02 fixed for the MAVLink ports, where an unauthenticated port on a routable interface let anyone arm the vehicle.

3 · It crashes, not degrades

When the API call fails the ROS context is torn down and a timer handle throws (exit 250). Worth knowing before C-04 relies on it surviving a simulator hiccup.

What this accidentally proved

The node initialises ROS, brings up its publishers (barometer, GPS, IMU, magnetometer), sets itself to DRONE mode, negotiates the real AirSim RPC protocol against a real UE-based server, and reports a version mismatch correctly. That is considerably more than "it compiles".

05 Going further: a stub server

C-06 only asked whether the wrapper compiles. But three questions C-04 will need do not require the engine, because they are answered entirely on the wrapper side. The AirSim client speaks plain msgpack-RPC, so a stub can impersonate the server: scripts/airsim_rpc_stub.py.

What this is not

A test fixture, not a simulator. Every value it returns is fabricated by that file. It proves how the wrapper transforms input; it says nothing about how AirSim behaves, and it does not substitute for C-02. The port is a ROS parameter (host_port), so the stub ran on a spare port and the CARLA instance on 41451 was never touched.

Entirely disjoint from Lane A's /fmu/*, as expected. Note odom_local and the two vel_cmd_* command topics — those are exactly what would tempt someone to bypass PX4, which coupling lane-c-topic-parity exists to prevent.

Q2 — the /clock trap: worse than expected

There is no clock topic at all — not /clock, not /airsim_node/clock. publish_clock defaults to false, so by default nothing publishes a clock.

A stack setting use_sim_time:=true against this wrapper as-shipped gets frozen timers and a node that hangs looking exactly like a deadlocked controller — precisely the P1-03a failure, arriving from a different direction.

Q3 — NWU vs ENU: answered from source, not runtime

The stub never got far enough to publish odometry, so this is static evidence, not a measurement. It is still conclusive:

odom_msg.pose.pose.position.y    = -odom_msg.pose.pose.position.y;
odom_msg.pose.pose.position.z    = -odom_msg.pose.pose.position.z;
odom_msg.pose.pose.orientation.y = -odom_msg.pose.pose.orientation.y;
odom_msg.pose.pose.orientation.z = -odom_msg.pose.pose.orientation.z;
// ... and the same for linear and angular twist

y and z negated, x untouched — that is NED → NWU. ENU would additionally swap x and y. And convert_tf_msg_to_enu() is defined at line 1600 and called from nowhere:

1600: void AirsimROSWrapper::convert_tf_msg_to_enu(...)   ← definition only
1636 / 1653 / 1670 / 1687 / 1706: convert_tf_msg_to_ros(...)   ← every actual call

So upstream's doc claim — "the right-handed coordinate frame of the ROS standard" — is wrong, and anything written against REP-103 will be yaw-rotated 90°. A runtime confirmation is still worth one ros2 topic echo in C-02.

Where the stub ran out of road, and why I stopped

Every nested struct must be complete — an empty {} throws std::bad_cast rather than defaulting. Each iteration was one crash:

#Failing callFix

The fifth is a different class — a DDS serialization fault from a string field, most likely the segmentation-label plumbing the stub feeds with empty arrays. Chasing it means reimplementing more of AirSim's surface, which is exactly the "don't reinvent upstream" line, for a question C-02 answers for free.

Two of three answered, the third answered statically, and the stub kept — ~200 lines that already drive the wrapper to full initialisation, and the cheapest way to exercise wrapper-side behaviour without a 24 GB image. Its limits are written into its own docstring.

Two process notes, because both wasted time

pkill -f airsim_rpc_stub killed the shell running it — -f matches the whole command line, and my own command contained that string. Then grep '[a]irsim_node' reported the node ALIVE when it had crashed, matching the grep's own command line.

Twice, the check was broken rather than the thing under test — the same shape as the find -type f false negative in § 03.

Two Positions,
One Aircraft

AirSim holds the vehicle’s position in two unrelated places — the physics integrator every PX4 sensor is derived from, and the Unreal actor the cameras are bolted to. When they came apart, the harness spent four minutes watching a drone descend through a city it had already landed on, and then blamed the flight controller.

01 The fault, drawn from its own trace

Every run since 2026-08-12 records both positions at 5 Hz. This is citysample-sensors-seed1, 2026-08-27, exactly as the probe wrote it: the two lines are one line through takeoff, the four waypoints and the start of the descent — and then the actor stops dead at 0.757 m and the integrator keeps going.

Because AirSim synthesises every sensor PX4 receives from the integrator — IMU, GPS, barometer, magnetometer, the rangefinder, LiDAR — nothing in the ROS 2 graph can contradict it. PX4 was told it was falling at 0.7 m/s, so it never disarmed, so LAND ran out its budget and the run reported timeout in state land: a control failure, on the flight whose waypoint errors were the best of its gate.

Why this is the worst possible report

This project’s premise is bring your own .uproject. A stranger flying their own world hits this and reads “success rate 0%, control failure” — a sentence about their aircraft, describing a fault in the simulator’s ground lock.

02 Detecting it, and the four things that must not trip it

SplitWatch in probe_landing.py is pure arithmetic over samples the probe already takes. It trips on dz ≥ 1.0 m, held ≥ 1.0 s across ≥ 3 samples, while vz ≥ +0.1 m/s (NED: positive is down).

04 Ending the flight without destroying the evidence

The obvious move — pkill -INT the controller — is wrong. rclpy raises KeyboardInterrupt past _write_result, so the run would forfeit waypoints_reached, the per-waypoint errors and the terminal MissionStatus. On exactly the runs this fires for, that is the evidence proving the aircraft was not what failed.

The abort check runs before the state timeout in _tick. Both end the flight; the order decides which sentence the report carries, and a split reaches the two at the same moment.

05 Two bugs, both found by running it

The classes were replayed against the real CitySample trace — watcher, abort file, and the parse the controller performs — rather than read and trusted.

1 — a name collision with Thread

self._stop = threading.Event() shadows threading.Thread._stop, the internal method join() calls. Every flight would have ended with TypeError: 'Event' object is not callable out of the finally block.

2 — the diagnosis overwritten by its own label

{"reason": reason, **rec} — and rec carries its own short reason, spread last. The controller would have failed with four words and no measurement, in the one field this whole change exists to fill.

Neither was visible by reading. Both are now pinned by tests, and the second is the “verify by running it” rule in miniature: the code was correct in shape and wrong in the only part anyone reads.

A third bug, and the flight is what found it

The probe’s summary line — the only place the split verdict is reported — never printed. pkill -INT lands in the time.sleep at the bottom of the loop, not in the RPC call that had the handler, so a traceback replaced it. Pre-existing, and the file’s own docstring claimed the line always printed. It did not. The whole loop is now inside the handler.

Stack torn down with ./scripts/sim_up.sh --down and verified independently with docker ps -a: containers, processes, display and GPU all clear.

07 The verdict: VOID, not FAIL

The owner’s call, and the same one the stale-EKF-origin check makes. A void is excluded from the success rate and blocks the criterion outright, so it is the stricter verdict, not the softer one.

BucketMeansEffect
PASSflew and landedcounts toward the rate
FAILthe aircraft did not do its jobcounts against it
VOIDthe rig broke — the run says nothing about the aircraftexcluded, and blocks the gate

A successful run is voided too, deliberately: a landing that terminated while the two poses disagreed by more than a metre is not a pass with a footnote — every camera frame in that bag shows a world the vehicle’s own state was not in. In the gate, the split reason outranks a sensor void, because a run stopped mid-mission easily records nothing on a requested sensor: “no messages on /camera/depth” is the consequence, the split is the cause.

A claim corrected rather than defended

The gate comment, this worklog and a test all described a precedence between the split reason and the sensor reason that the pipeline cannot produce. The ordering is defensive, and now says so. The real consequence was elsewhere: a split-voided run reached the report with sensors_empty populated and its explanation only on a stderr line. It is recorded as sensor_evidence_note now.

Re-scored after the skew change, the 91 traces still give 9 tripped, 82 clean — a missing gap means no correction, which is exactly how those traces were first scored. Suite: 231 pass. Known limitation, recorded rather than hidden: the detector is phase-blind, so a split on a descending waypoint leg would still be called a landing-surface rejection.

09 What this deliberately does not do

It does not prevent the split. Only one branch in FastPhysicsEngine.hpp stops a descent — the ground lock at :228 — and reaching it requires the engine to recognise the contact as ground entirely from the collision normal (:156, kAxisTolerance = 0.25). A coarse HLOD proxy such as FastGeoSurrogateActor_0 plausibly supplies an off-axis normal; Blocks’ flat plane cannot express the fault at all, which is why 40 Blocks seeds found nothing.

Still unmeasured

Which of the two gates actually aborts — the :141 early return or the :156 normal test — has never been observed. That is step 1, it needs one throttled log and one seeded flight, and it decides what step 3 should be.

Step 2 earns its place regardless: it is also the instrument that will say whether step 3 worked.

01 The finding is not the test fix

Noticed while merging PR 64: gh pr checks said off-target-tests fail. The reflex is to look at the branch. The branch was not the problem — main was, and had been since 2026-08-18.

The rule this earns

If the required check is red: either the branch broke it — fix the branch — or main is already broken, and then that is the work, and it comes first.

02 Why it could never have passed

Two tests needed vendor/Cosys-AirSim/.../Blocks.uproject to exist, because resolve_world ends in if not p.is_file(): sys.exit(...). vendor/ is gitignored — it arrives in quickstart step 0.2, long after CI runs.

world not found: vendor/Cosys-AirSim/Unreal/Environments/Blocks/Blocks.uproject
  (resolved to /home/runner/work/drone-sim/drone-sim/vendor/.../Blocks.uproject)

— naming a file that plainly exists on the workstation. They could only ever pass on a machine that had already built the vendored tree, which is not a test a gate can use. Same family as SIM-37’s COPY vendor/: work that assumes a tree CI does not have. That one broke fresh-clone builds; this broke the gate, which is quieter and worse.

03 The fix, and checking it the right way

Root world resolution in a throwaway tree that has a Blocks.uproject in it. That keeps what the tests protect — a relative world: anchors to the repo rather than to the caller’s cwd — and drops a dependency on 2.4 GB of vendored source. The third case was added explicitly, since it was the behaviour those two protected and was only ever implied.

Running the suite in place proves nothing

In place, the file exists. So the tree was copied without vendor/ and the suite run against that copy: 206 passed, against 2 failed, 203 passed for main’s version.

The first attempt at that check was itself wrong, and it is the same shape as everything else here: rsync --exclude=vendor is unanchored, so it also dropped docs/vendor/, and an unrelated test failed. A check that cannot see what it thinks it is checking looks exactly like a real failure — the same trap as pgrep -x silently seeing nothing, and as the counters in SIM-38.

04 From review

Review reproduced the seven red runs independently, mutation-tested that the rewritten tests still fail when the REPO anchoring is removed, and confirmed the rs.REPO patch cannot leak between tests. It also caught that the helper faked only REPO: SIM_UP, RECORD_CHASE and APPLY_PARAMS are derived at import time and still point at the real repo, so a later test reusing it as a general “fake repo” would silently run the real record_chase.sh on the workstation. Renamed to say what it actually does. And it asked for this page, on the grounds that the durable finding was sitting only in a commit message.

§ 2 · UPSTREAM DRIFT

The pinned XRCE agent cannot be built

The development plan pins Micro-XRCE-DDS-Agent v2.4.2. It is unbuildable on this platform by either available route.

RouteOutcome
v2.4.2 superbuild (upstream default)fails at clone fatal: invalid reference: 2.12.x — eProsima deleted the Fast-DDS branch it pins
v2.4.2 + Fast-DDS tag v2.12.2fails at compile 'uint8_t' in namespace 'std' does not name a type — the 2.12 line predates GCC 13
v2.4.2 + system Fast-DDS 2.14.6segfaults builds clean, then dies creating DDS entities → 0 topics
v2.4.3 + system Fast-DDS 2.14.6works next release, pins Fast-DDS 2.14 — the generation Jazzy ships
Why this matters beyond the fix

v2.4.2 pins its dependency by branch, not SHA. Upstream deleted the branch, so a tagged, immutable release became unbuildable retroactively — through no change of ours. This is precisely why versions.lock requires a SHA: a branch is not a pin.

Resolved with no source patch — v2.4.3 built against Jazzy's Fast-DDS via -DUAGENT_USE_SYSTEM_FASTDDS=ON. Deviation recorded in vendor/Micro-XRCE-DDS-Agent/LOCAL_PATCHES.md. Consequence: the binary links /opt/ros/jazzy/lib/libfastrtps.so.2.14, so ROS 2 must be sourced for the agent to run.

§ 3 · PLAN CORRECTION

Airframe targets need the gz_ prefix

The plan names x500_lidar_2d, x500_lidar_front, x500_lidar_down. Those targets do not exist — every real target is gz_-prefixed, so make px4_sitl x500_lidar_2d simply fails. Enumerated from the built tree rather than trusted from memory.

Two finds the plan never mentions

gz_x500_vision (4005) is a purpose-built vision/VIO airframe — very likely a better Phase 3 starting point than bolting a camera onto gz_x500. gz_x500_flow (4021) gives optical flow, directly relevant to GPS-denied work. Both should be evaluated before writing a custom airframe.

The flagged risk did not materialise

The Accel #0 fail: TIMEOUT! failure tracked in PX4/PX4-Autopilot#25089, #24595 and rated Med/Med for this exact Ubuntu 24.04 + Harmonic combination did not occur. All four documented mitigations were applied up front rather than after a failure: single-command launch, GZ_IP=127.0.0.1 (loopback transport), HEADLESS=1, and 24 cores of headroom. The isolated netns likely helps too — the documented root cause is Gazebo multicast flooding the host network, and this container cannot reach it.

P0-06 closes here too. A green colcon build never proved the px4_msgs branch match — 24 topics publishing at a stable 100 Hz does. A mismatch produces topics that exist and stay empty, which is exactly what a build cannot detect.

§ 5 · GUI VERIFICATION

QGroundControl on a virtual display

The container has no usable DISPLAY — an X0 socket exists but X authorization rejects us (Authorization required, but no authorization protocol specified). Rather than declare the criterion unverifiable, run it on a virtual display and screenshot the result.

Xvfb :99 -screen 0 1600x1000x24 -nolisten tcp &
DISPLAY=:99 QT_QUICK_BACKEND=software LIBGL_ALWAYS_SOFTWARE=1 QT_QPA_PLATFORM=xcb \
  ./vendor/tools/QGroundControl.AppImage &
DISPLAY=:99 import -window root shot.png

QT_QUICK_BACKEND=software is required — Xvfb has no hardware GL and QtQuick will not initialise without it.

Result: "Ready To Fly", flight mode Hold, battery 100%, autopilot detected as PX4, live compass, map at the SITL default home (Irchelpark, Zurich — 47.397 N, 8.545 E). Evidence: assets/2026-07-28-p0-08-qgc-connected.png.

Reusable

This recipe generalises to any GUI in this container — rviz, Foxglove, the Gazebo GUI. "No display" is no longer a reason to leave a criterion unverified.

§ 6 · GOTCHA

The GPU-pinning gotcha

vLLM 0.26.0 installed cleanly with torch 2.11.0+cu130, and its arch list includes sm_120 — so Blackwell needs no cu128-nightly workaround, a risk the hardware assessment raised that turns out not to apply.

But CUDA_VISIBLE_DEVICES=1 alone does NOT pin the 5060 Ti

vLLM warns on every import here: "Detected different devices in the system: NVIDIA GeForce RTX 3080, NVIDIA GeForce RTX 5060 Ti. Please make sure to set CUDA_DEVICE_ORDER=PCI_BUS_ID to avoid unexpected behavior."

CUDA's default ordering is FASTEST_FIRST, not PCI bus order. With two dissimilar cards, index 1 is not reliably the Blackwell card. The GPU work split (render on 0, infer on 1) is a hard project rule, and the docs describe enforcing it with CUDA_VISIBLE_DEVICES alone — which is insufficient. Set both variables and verify against nvidia-smi.

Also confirmed: GPU 1 is the 16 GB variant (16311 MiB), resolving an open question in the hardware assessment — Qwen3-VL-8B AWQ is viable locally with KV headroom, not just 2B/4B.

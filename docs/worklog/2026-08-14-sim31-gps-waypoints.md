# 2026-08-14 — GPS waypoints, without touching the controller

**`SIM-31`, slice three.** The last of the five capabilities, and the one the design called *"the
only piece needing controller changes."* It didn't.

**Headline: a 10 m square expressed in GPS coordinates converted back to exactly the same square
in metres, and flew 4/4 — with no change to `offboard_control`.**

---

## Why it looked like a controller job

PX4 has **no global setpoint message**. `verify_nav_interface.py:15` had already recorded it:
`GotoSetpoint` is local NED, and `VehicleGlobalPosition` is an estimate *output*, not a command.
So a lat/lon has to become a local coordinate somewhere.

The assumption was that "somewhere" is the controller. It isn't — it just has to happen **before
the setpoints start**, and `run_scenario.py` is already there, already talks to the stack, and
already writes the provenance. Converting there keeps the flight code untouched.

## The reference is the whole problem

Everything about this slice turns on *which* reference the conversion uses. Measured yesterday, on
this stack:

| | latitude | longitude | altitude |
|---|---|---|---|
| declared `OriginGeopoint` | 37.412300 | −121.995000 | 50.0 m |
| PX4 EKF `ref_*` | 37.4123278 | −121.9948484 | 51.28 m |

**13.8 m apart.** Converting against the declared origin would put every waypoint ~14 m off — an
error shaped exactly like a control failure, on a stack where nothing is wrong.

So the conversion reads `ref_lat`/`ref_lon`/`ref_alt` from `/fmu/out/vehicle_local_position`. That
reader already existed in `check_ekf_origin.py`, including the BEST_EFFORT QoS handling any second
copy would have had to duplicate, so it gained a `--print-ref` mode rather than a sibling.

## Matching PX4's projection, not a better one

The maths is `MapProjection::project` — azimuthal equidistant on PX4's sphere,
`R = 6371000`. Using a more accurate ellipsoid would be *worse*: the target frame **is** PX4's, so
any disagreement in Earth model becomes a position error the aircraft cannot see.

Unit-checked against known distances before flying anything:

```
origin itself        ->  E 0.000   N 0.000    U 0.000
+0.0001 lat, +20 m   ->  E 0.000   N 11.119   U 20.000
+0.0001 lon          ->  E 8.832   N 0.000    U 0.000
```

11.119 m per 0.0001° latitude, and 8.832 m per 0.0001° longitude at 37.4° — which is
`111320 × cos(37.4°) × 0.0001`.

## The test is a round trip, deliberately

Declaring arbitrary GPS coordinates would prove the aircraft flew *somewhere*. Instead the
scenario's waypoints are generated by inverting the projection on the known square, so the
conversion has to give the square back:

```
37.4123278, -121.9947352, 71.28 m  ->  E +10.00  N  +0.00  U +20.00
37.4124177, -121.9947352, 71.28 m  ->  E +10.00  N +10.00  U +20.00
37.4124177, -121.9948484, 71.28 m  ->  E  +0.00  N +10.00  U +20.00
37.4123278, -121.9948484, 71.28 m  ->  E  +0.00  N  +0.00  U +20.00
```

Exact. Flight: **4/4 waypoints**, errors 0.801 / 0.769 / 0.789 / 0.783 m — indistinguishable from
the same square declared in ENU, which is the point.

## Two things refused rather than guessed

- **A scenario declaring both `waypoints_enu` and `waypoints_gps` is an error.** There is no
  defined precedence, and picking one silently flies the wrong mission.
- **The conversion is pinned at one moment.** If PX4 re-initialises its EKF origin mid-flight the
  waypoints are stale, computed against the old reference. Acceptable for a single sortie, not for
  a long one. Written down rather than guarded — a guard nobody has seen fire is not evidence.

## Provenance

The run JSON records `waypoints_gps`, `ekf_ref` and `waypoints_enu_flown`, so the conversion can
be re-derived from the result rather than trusted.
